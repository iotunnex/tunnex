# 1. SCOPE, FIXED BY MEASUREMENT — argued here so it is not re-derived later

The registration paper's cost model was refuted by its own measurement pass. The scope below is what survived,
with citations, and it is the reason this is a commit-one about a **principal** and not about a destination.

## 1.1 The destination half is ALREADY SHIPPED

`resources` carries `cidr` + `protocol ∈ {any,tcp,udp}` + `port_low`/`port_high` under live CHECKs
(`resources_check`, `resources_port_low_check`, `resources_port_high_check`). **An MCP server at
`10.1.2.3:8080/tcp` is expressible today, with zero schema change**, as a `resource` with
`protocol=tcp, port_low=port_high=8080` referenced by the existing `dst_kind='resource'`.

⛔ **AND A NEW `dst_kind` WOULD BE INVISIBLE TO ENFORCEMENT BY CONSTRUCTION.** `hashAllow`
(`apps/api/internal/policyspec/hash.go:15-21`) is exactly five fields — `{SrcIP, DstCIDR, Protocol, PortLow,
PortHigh}`. **`dst_kind` never reaches the compiled artifact.** By the time enforcement sees a destination it
is resolved addresses and ports; a `resource` and a hypothetical `mcp_server` are indistinguishable to it.

**The `k8s_service` precedent claim is struck.** `policy_rules` uses a **discriminator column per kind** under
an exclusive-arm CHECK (`policy_rules_check`), so a new kind costs a new column + two constraint rewrites +
compiler resolution + goldens — **to add something enforcement cannot see.**

**No version bump, structurally.** `RequiredVersion` (`apps/api/internal/policyspec/policyspec.go:128-149`)
triggers only on `VIPMappings`/`K8sDNSZones`→7, `PoolCIDR`→6, `Routes` or a CIDR `SrcIP`→5, else 4. A
CP-resolved destination emits an `AllowEntry` **byte-identical in shape** to a resource's — nothing for an old
agent to fail to understand, therefore nothing to refuse.

## 1.2 The audit half is INHERITED — conditionally, and the condition binds

`src_device_id` is **agent-stamped from the compiled artifact's `/32`→device map**; the CP performs one FK
join to `src_user_id` (`apps/api/internal/accesslog/ingest.go:40-75`). Explicitly **not** an `src_ip` lookup.

⛔ **THE CONDITION: attribution works IFF the principal is a `/32` the artifact maps to a device.** A
principal shape that is not address-bearing goes dark on attribution **silently — the flow log will not
complain.** That is a constraint on the principal design (**D15**), not a property of the audit layer.

## 1.3 The principal IS the epic

`devices.user_id` carries **three loads at once**: the per-user device cap
(`apps/api/db/queries/devices.sql:98-104`), the posture cut's *"which human account launched it"*, and any
future delegation link. **One column, three questions.**

`machine_credentials` has **no `user_id` column** — live schema: `id · org_id · name · role · token_hash ·
fingerprint · created_at · last_used_at · revoked_at`.

> ## **THE DESTINATION HALF IS SHIPPED. THE AUDIT HALF IS INHERITED. THE PRINCIPAL IS THE EPIC.**

# 2. WHAT THE SELF-HOSTED INDUSTRY ACTUALLY DOES

Written against sources rather than memory, because this is the section that stops us re-inventing.

## 2.1 Teleport — `rfd/0209-mcp-access.md`, implemented in 18.1

MCP servers are registered as **apps** under the existing Application Service — deliberately reusing HTTP/TCP
app machinery rather than building a new service. The connection handler parses the stream into JSON-RPC
messages and tracks type by message id.

**The enforcement shape, and it is the part to copy:**

- on `tools/call` — check the access-checker; **if denied, synthesise an error result and return it to the
  client without forwarding upstream**
- on the response to `tools/list` — filter out tools the identity may not call
- ⛔ **THEY DO BOTH, AND THEY SAY WHY: filtering the list is not enforcement, because nothing prevents a
  malicious client from calling a tool that was never listed.**

**Audit:** `mcp.session.start`/`.end`, `mcp.session.request`, `mcp.session.notification`; a denied
`tools/call` carries the error. **`tools/list` and `resources/list` are deliberately NOT recorded — too
frequent.** ⚠ Note for us: that is a real tension with a flow-log product, and it is a considered choice
rather than an oversight.

⛔ **AND A DEFAULT FLIPPED BETWEEN PAPER AND PRODUCT, IN THE DIRECTION WE SHOULD COPY.** RFD 0209 specifies
that if `mcp.tools` is unspecified, **all tools are allowed**. The shipped documentation says **no tools are
allowed if unspecified**. They moved from fail-open to fail-closed between design and ship. **Take the shipped
default.**

## 2.2 Octelium — the transferable method

**No bespoke MCP engine.** MCP is treated as JSON-RPC over HTTP and generic L7 body policy is applied — a CEL
expression over the parsed body (`bodyMap.method == "tools/call"`, `params.name in [...]`, argument-level
predicates), gated on request buffering with a max size. Argument-level policy falls out for free.

⚠ **AND THE GAP IS INSTRUCTIVE: no `tools/list` RESPONSE filtering was found in their MCP guide.** So a client
sees tools it cannot call and discovers the boundary by hitting a refusal. **Enforcement is the request half;
catalog filtering is the UX half. Shipping only the second would be the defect; shipping only the first is
defensible and must be SAID.**

## 2.3 agentgateway — Linux Foundation / Agentic AI Foundation

Rust data plane, Cedar policy, **tool federation** — one endpoint fronting many MCP servers with a per-client
virtual catalog. Their founding argument was that MCP's **statefulness** defeats ordinary gateways: long-lived
sessions, server-initiated messages, `tools/list` fan-out needing per-session response adjustment.

⛔ **`2026-07-28` substantially undercut that argument** — stateless core, `Mcp-Session-Id` retired. Their
federation value stands; the "you need a new kind of proxy" claim does not, to the same degree.

## 2.4 What NONE of them has — and the honest bound on our claim

**Cross-organisation delegation.** agentgateway says so in its own framing: it is governance **for your trust
domain**, and the cross-org trust layer (DIDs, verifiable credentials, delegation chains surviving an org
boundary) is still missing across the field.

> **Intra-org agent identity is PARITY, not catch-up. The paper must not imply the cross-org half.**

# 3. DECIDE-ITEMS — surfaced, recommended, **HELD**

## ⭐ D14 — the ruling everything else waits on

**`machine_credentials` has no `user_id`. Every machine principal shipped today is ALREADY OWNERLESS.**

> ## **THE QUESTION IS NOT "PERMIT OWNERLESS AGENTS". IT IS "KEEP THE OWNERLESS PRINCIPAL WE ALREADY HAVE."**

**The mechanical argument, which replaces the philosophical one:**

> **An ownerless agent is outside the cap query (`user_id`-keyed), outside any delegation link, and STILL
> INSIDE THE POOL. It costs the scarce thing and escapes both accountable ones.**

⚠ **AND DELEGATION EXISTS IN NEITHER LAYER.** `audit_logs` carries `actor_user_id` and `actor_system` as
**parallel columns, not a chain** — an event is attributed to a human OR a subsystem, never *"this system
acting for that human"*. `X-Tunnex-Cause` (S10.2) supplies **which CR triggered this**: provenance of the
TRIGGER. Delegation is provenance of the AUTHORITY. **The operator has the first and not the second.**

**RECOMMENDATION (HELD): bind to an owner.**

⛔ **THE MIGRATION CONSEQUENCE, STATED HONESTLY — THIS IS A CHANGE TO SHIPPED BEHAVIOUR.** Machine credentials
exist in production today with no owner. Binding requires deciding what happens to them: back-fill to the
minting user (if recoverable), require re-mint, or grandfather them as a named exception. **Grandfathering
would leave the ownerless principal alive under a different name**, which is the outcome the ruling is meant
to close. This is not a greenfield choice and must not be costed as one.

## D4 — a new `agent` role, not `operator`

`RoleOperator` holds `PermPolicyManage` (`apps/api/internal/rbac/rbac.go:141`) — a machine principal can
author its own access rules, and the role is **fixed at mint** (`apps/api/internal/machineauth/service.go:83`).

**Blast radius, measured:** `RoleOperator` appears in **four files** — the grant table (`rbac.go`), the mint
site (`machineauth/service.go`), and two tests — plus the generated `apps/web/src/lib/rbac-policy.json`,
drift-guarded by `make generate-rbac` / `make generate-check`. **One grant-table entry, one mint site, one
regenerate, two test updates. No spec change.**

⚠ **RECORD THE CONDITION, NOT JUST THE COUNT: it is cheap BECAUSE machine roles are not user-assignable.**
If agent roles ever become operator-assignable, the blast radius changes shape entirely — spec paths, the RBAC
matrix, the 401-walk. **The next reader will otherwise inherit "cheap" without its precondition.**

**RECOMMENDATION (HELD): a new `agent` role. Not `operator`.**

## D15 — is the agent address-bearing?

**Binding, not preference.** Attribution rides the artifact's `/32`→device map
(`apps/api/internal/accesslog/ingest.go:40-75`). **A principal design that avoids the `/32` goes dark on
attribution, silently, and the flow log will not complain.**

**RECOMMENDATION (HELD): address-bearing.**

**THE COST, NAMED:** every agent takes one address from the org pool. `organizations.pool_cidr` defaults to
**`10.99.0.0/24`** — a hardcoded column default — and `ipalloc.go` reserves network, gateway and broadcast,
leaving **253 allocatable addresses, org-wide, shared with every human's devices.** Exhaustion is a hard
refusal (`pool_exhausted`, `apps/api/internal/devices/service.go:296`).

⚠ **Each agent is within the per-user cap and the fleet collectively exhausts a shared pool** — the same
org-pool DoS the cap convention was written against (`devices.sql:100-101`), arriving through a door the cap
does not watch.

## D16 — pool default and headroom

⛔ **NOT A CEILING.** `pool_cidr` is resizable (`organizations.sql:56`), the resize has a UI
(`apps/web/src/pages/Settings.tsx:407-435`), and S4.5b's grow-superset path with its orphan check is proven.
A `/16` is 65,534 addresses. **Addresses are free.**

**THE FINDING IS THAT NOTHING SURFACES UTILISATION.** `apps/web/src/lib/poolview.ts` exports only
`orphanReasonCopy` and `orphanTail`. There is no used/total, no headroom, no warning at 80%. **The resize verb
is reachable and the signal that it is needed is missing** — the S14.12 verb-census class, one turn worse.

**RECOMMENDATION (HELD): register separately. Do NOT fold it into this epic.** It is true for laptops today
and independent of agents. ⚠ It is also the first concrete trigger the deferred **IPv6 pool** item has had.

## D17 — sequencing

`PLAN.md` locks EPIC 15 as an epic between EPIC 14 and the beta bundle. **That lock was made when the
destination half looked like new enforcement machinery. It is not.**

> **THE BUILD SHRANK AND THE DECISIONS DID NOT.** What remains is a principal design plus UI; the expensive
> part is D14 and D4, which are **founder-time, not build-time.**

**RECOMMENDATION (HELD): none — this is a ruling, not a finding.** Whether it becomes a story slotted cheaply
or stays an epic because the rulings deserve the ceremony is the founder's call. **This paper does not edit
the build order.**

## D18 — MCP revision support, and stdio

**Both `2025-11-25` and `2026-07-28` are live, with a 12-month deprecation window on the legacy transport.**
`2025-11-25` uses `Mcp-Session-Id` and the `initialize` handshake; `2026-07-28` retires both and requires
`Mcp-Method`/`Mcp-Name`. **A design that assumes one revision is wrong on arrival.**

**S8.1's fail-closed version gate is the pattern** — refuse an artifact whose version you do not speak, loudly,
rather than half-understanding it. Applied here to somebody else's protocol.

⛔ **stdio IS OUT OF SCOPE, AND THE REASON MUST BE STATED PUBLICLY.** A stdio MCP server is a **child process
of the client on the same host** — there is no network to police, and a network zero-trust platform has
nothing to enforce there. Teleport moved *execution* onto their own service host precisely to obtain a
boundary. **Say this rather than letting "MCP support" imply stdio.**

**RECOMMENDATION (HELD): support both HTTP revisions behind a fail-closed gate; stdio out, stated.**

# 4. LAWS PRE-REGISTERED — naming them now makes noticing them cheap

Each is a prediction. All are already in `docs/laws.md` in another domain.

| law | how it will present here |
|---|---|
| ⛔ **A GUARD MUST BE EXERCISED THROUGH THE STACK IT RUNS IN** | authorizing on `Mcp-Name` without checking the body. The headers are **mirrored from the body and the body stays authoritative** — so header-only authorization is authorizing on a **client-supplied claim**. `middleware.RealIP` one protocol over, and worse, because this header is *designed* to look authoritative. **The single highest-risk defect in the epic** |
| **INVISIBLE IS NOT ABSENT** | filtering `tools/list` and calling it enforcement. Teleport says explicitly that it is not: nothing stops a client calling an unlisted tool. **A filtered catalog is a presentation decision; only the call check is an access decision** |
| **ABSENCE MUST BE THE CLOSED STATE** | an unspecified tool list meaning *all tools*. Teleport shipped the opposite of their own RFD here — **take the shipped default** |
| **A FIXTURE THAT ENCODES THE ANSWER IN THE NAME** | fixtures named `tool-allowed` / `tool-denied`. That is `gw-active`/`gw-revoked` again, **already paid for once** |
| **RENDER FLOOR AT PRODUCT SCALE** | any **AP2** claim. AP2 is not a third protocol — signed mandates carried inside A2A/MCP, FIDO-governed since April 2026, no wire of its own. **No "AP2 support" bullet**: the SOC 2 badge, one domain over |
| **THE MORE A VIEW EXISTS TO SURFACE A PROBLEM, THE MORE DANGEROUS ITS EMPTY STATE** | an A2A Agent Card fetch that fails rendering as *"this agent offers no skills"* |
