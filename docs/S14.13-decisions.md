## ⛔ THE SESSION'S FINDING — the wireframe is wrong about what it DEPICTS

The design instructs `_tunnex-verify.acme.io TXT "tnx-domain-9c44…"`. `txtHasToken`
(`enterprise/sso/domain.go:175`) resolves the **APEX** with no prefix and compares by **exact
equality** against `"tunnex-verify=" + token`. **Both halves differ.** An operator following the
design publishes at a subdomain the resolver never queries, carrying a prefix the comparison never
matches, and then watches Verify fail forever with the record visibly present in their zone.

> ## **THE ABSENCE QUESTIONS ASSUME THE DESIGN IS RIGHT ABOUT WHAT IT DEPICTS. HERE IT WAS NOT —**
> ## **AND A PANEL-BY-PANEL DIFF WOULD HAVE COPIED THE DEFECT FAITHFULLY.**
> Instance of the existing **measure-before-acting** law; the new part is only *where* the wrong
> value came from — the design itself, not memory. Both wireframe forms are now pinned as WRONG in
> `domainview.test.ts`, so a "match the design" edit fails in CI rather than in a customer's DNS zone.

## REFUTED — a premise carried into the build

**`resize_conflict` exists NOWHERE in the repository.** Not in the spec, handlers, or generated
types. The 409 body is a bare `ResizeConflict` (`openapi.yaml:2883`) — `orphan_count` + `orphans`,
**no `code` field**; the client duck-types it precisely because there is none. Rendering it verbatim
would print an identifier no support engineer could grep, in the one place an operator would copy it
from. **NOT rendered** — `RESIZE_CONFLICT_HAS_NO_CODE` holds the finding instead of the string.
