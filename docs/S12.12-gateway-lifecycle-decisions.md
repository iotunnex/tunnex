# S12.12 — Gateway lifecycle: transfer, delete, edit

**Commit-one is paper.** These decisions are ruled BEFORE product code, per the story protocol. The
founder ruled D1–D3 in-session; the measurements below are what the rulings were made against, and every
one of them was taken from the code rather than from a handoff.

---

## The observation that started it

A gateway was revoked. Its devices read `revoked`, and the operator had not revoked them.

**That is what the code does, and it is not a defect.** `nodes/service.go:2346` runs
`RevokeDevicesForNode` INSIDE the same transaction as `RevokeNode`, sweeping `active` + `pending` and
stamping `revoked_cause='cascade'`. The founder's observation confirms the cascade; it does not
contradict it.

⚠ **A handoff claiming devices stay active with `revoked_at` NULL is wrong.** The code is the record.
Recorded here because the same claim has now cost two sessions.

## D1 — TRANSFER HAPPENS BEFORE REVOKE, AS ITS OWN STEP. **RULED.**

⛔ **Not a warning that counts devices — a step that moves them.** Pick a destination gateway, move the
devices, then revoke.

⛔ **Revoke does not proceed while devices are still homed there.** The refusal names the count and offers
the transfer.

### Why not cascade-then-restore (the shape that already exists)

`restoreNodeDevices` could technically serve this: revoke, then restore the cascade-revoked devices onto a
new gateway. **Rejected, and the reason is the failure mode, not the elegance:**

⚠ **It leaves a window in which every device is disconnected**, and if the operator abandons halfway —
closes the tab, loses the network, is interrupted — **the gateway is revoked and the devices are stranded
with no un-revoke.** There is no way back: un-revoke is permanently refused by ruling.

⭐ **Transfer-first means nothing breaks even if they walk away.** The half-done state is "devices moved,
old gateway still running", which is harmless and resumable. The half-done state of the other order is an
outage the product cannot undo.

> **A multi-step destructive flow is designed around the state it is abandoned in, not the state it ends
> in.** The operator who walks away mid-flow is not an edge case; they are the case that decides the order.

### What this requires (none of it exists)

1. A transfer verb: move `active`/`pending` devices from node A to node B.
2. Validation that the target is LIVE and its pool has capacity for the incoming devices.
3. Address reassignment — the devices' `/32`s come from the pool, and the target may collide.
4. Peer-set reconcile on BOTH gateways.
5. `Revoke` refuses while `CountDevicesForNode(active|pending) > 0`, with a typed refusal naming the count.
6. Config staleness: every issued config carries its gateway. A transferred device's config is stale by
   the `needs_reexport` GATEWAY cause — static exports cannot be re-pointed and must be re-issued;
   a managed device re-homes through the dial channel. `openapi.yaml:3891`.

⚠ **(6) IS THE PART THAT WILL BE UNDER-SCOPED.** Moving the row is the easy half. A device whose config
still names the old gateway is moved in the database and broken on the wire.

## D2 — THE JOIN TOKEN IS CLEANED WITH THE DELETE, NOT A BLOCKER. **RULED.**

⭐ **The sequence already made this safe:** devices transferred, gateway revoked, nothing homed. By the
time delete is reachable, the CASCADE columns have nothing left to destroy — which is what makes the
delete safe, not the FK actions themselves.

⚠ **Refusing a delete over a leftover enrolment token would make the NEWEST gateways the hardest to
remove** — a token is most likely to still exist on a gateway enrolled recently. That is backwards.

⛔ **AND THE CONFIRM SAYS WHAT A CLEANED TOKEN MEANS: if someone holds that token, it stops working.**
That is correct behaviour and the operator must know it, because the token may have been handed to a
colleague who is about to run the installer.

⚠ **Correction to the premise this was ruled against:** `node_join_tokens.consumed_node_id` is
`ON DELETE SET NULL` (`0008_nodes.up.sql:46`), NOT `NO ACTION`. **It never would have blocked the delete.**
The ruling stands unchanged — cleaning the token is still right, and saying so in the confirm is still
right — but it is a deliberate cleanup, not the removal of an obstacle.

---

## D3 — EDIT: BUILD BOTH, AND NOTE THE ASYMMETRY. **RULED.**

⚠ **Name is free.** Nothing consumes it structurally; it is a label on a row.

⛔ **Endpoint is not.** Peers hold it, and every issued device config carries it. An address change means
**re-issuing configs**, and the confirm must say so.

⭐ **The alternative, if address editing is deferred:** say plainly that the address is not editable and
re-enrolment is the answer — **but then the ceiling must not charge for it, since it is a correction, not
growth.** An operator fixing their own typo must not pay a licence slot for it.

⚠ **That clause is a real constraint on the ceiling code, not a nicety.** `CountLiveNodes` counts
`revoked_at IS NULL`; a correction-by-re-enrolment costs a slot until the old node is revoked, and the
operator hits the ceiling in the middle of fixing a typo.

---

## Build order

**Transfer first — it blocks everything else.** Delete is only safe once nothing is homed (D2's whole
premise), and the revoke refusal in D1 is what guarantees that.

Then: delete, then edit-name (independent and cheap), then edit-address (drags config staleness).

⛔ **AND THE CONFIRM'S COPY CHANGES WITH TRANSFER, NOT BEFORE IT.** Today the confirm says *"the devices
stop connecting immediately"*, which is **currently true** — the cascade is real. Once transfer is a step,
the operator has already moved them and the sentence becomes false.

⚠ **It is deliberately NOT being rewritten in advance.** Copy describing a flow the product does not have
is the exact defect recorded twice in `docs/laws.md` this cycle — the ceiling notice naming a Revoke
button that a layout decision had deleted, and the same notice calling a disconnection "tidy-up". The
sentence changes in the same commit that makes it false, and not one commit earlier.

## D4–D6 — the three remaining items. **RULED** (founder, in-session).

- **D4 — PENDING devices transfer too.** An outstanding approval is about the PERSON, not the gateway;
  leaving pending rows behind would strand an approval queue pointing at a gateway that is about to be
  revoked — the exact defect `RevokeDevicesForNode` already sweeps pending to avoid (`devices.sql:176`).
- **D5 — a different SITE is allowed.** ⚠ But site-scoped policy is evaluated against the device's
  gateway's site, so a cross-site transfer CHANGES WHICH RULES APPLY to that device. The transfer surface
  must say so; silently re-scoping someone's access is a policy change wearing a maintenance label.
- **D6 — ONE audit event, naming the count and both gateways.** Per-device rows would drown the log on a
  fleet move, and the operator's question afterwards is "what moved", singular.

⚠ **D5 IS THE ONE TO WATCH.** D4 and D6 are cosmetic — they change a filter and a row count. D5 changes
what a device is ALLOWED TO REACH, which makes it load-bearing rather than presentational: if the transfer
UI does not state the policy consequence, a cross-site move becomes a silent grant or a silent revocation.
Flagged here rather than resolved, because the surface that must carry it does not exist yet.
