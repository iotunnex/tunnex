## THE HARD RULE (D7) — the operator is an API CLIENT, never a DB writer

**`apps/operator` calls the existing CP HTTP API (the same handlers the dashboard calls). It touches NO
database and NO data plane.** This one sentence is the load-bearing invariant of the whole story: EVERY
ledgered guarantee — the Collect/OrgRanges disjointness validator, the identity↔credential binding, the
edition gate (403 `edition_required`), and the S10.3 H2 audit-with-cascade-counts — is inherited **for free,
and ONLY for as long as this holds.** A DB write, or a direct call into a service layer that bypasses a
handler's validation/audit, silently sheds all of them.

RED (census, must be greppable): `apps/operator` imports **no** DB package — no `pgx`, no `sqlc`, no
`apps/api/db`, no `apps/api/internal/*` service/store package. Its only inbound surface to Tunnex is the
generated HTTP client against `openapi/openapi.yaml`. A test/CI grep asserts the absence, the same shape as
the subnetguard census red (`TestCensusNoHandBuiltOrgRanges`).

Consequence for the design: the operator is a **thin controller-runtime translation layer** — CR → API call
→ CR status. It is NOT a data-plane contributor. The roadmap's implied data-plane job (supply authoritative
ClusterIPs, S10.3 Ruling B, `docs/S10.3-decisions.md:209`) was **SUPERSEDED** by WF-K5's gateway-local
endpoint watch (`docs/S10.3-decisions.md:616`) — there is no data-plane work left for the operator.

## Verify pass — the genuine delta (roadmap nouns RETIRED on evidence)

The roadmap (`PLAN.md:1451`) named S10.2 = an operator watching **`TunnexPeer`/`TunnexRoute`**, "reconcile WG
peers/routes as k8s resources, reuses the S3.1 reconcile loop." That framing is a mesh/WG-peer mental model
that **predates the S10.3 rulings** and is retired here on evidence (the third such re-scope this
programme — S9.2/S9.3 absorbed, S10.3 re-scoped, now this):

- **`TunnexPeer` — RETIRED, no backing.** Declaring a "peer" as a K8s object would require an **unowned
  peer** — but `devices.user_id` is `NOT NULL REFERENCES users` ("no unowned peers",
  `docs/EPIC10-decisions.md:27`), and **workload-as-source-identity was ruled OUT of EPIC 10 (D4)**. The only
  "peer" a cluster has is its gateway, which self-provisions zero-touch (join-token → enroll → CSR → mTLS →
  DesiredState), never declared per-peer. The roadmap noun would have required inventing the exact thing D4
  forbade. **This retirement is recorded so PLAN.md's stale line is not re-read as owed work.**
- **`TunnexRoute` — RETIRED as a noun (capability lives at a different granularity).** Shipped "routes" =
  the cluster's synthetic VIP range (`RegisterCluster`) + per-Service `/32` VIPs (`ExposeService`), all
  CP-owned. The declarable unit is the **cluster + exposed-service**, not a free-standing route object.

**The CRDs a platform team would actually write (RULED, D1) map 1:1 onto S10.3's shipped API verbs:**

| CRD | Backing CP verb (existing) | Tier |
|-----|----------------------------|------|
| `TunnexCluster` | `registerK8sCluster` / `deregisterK8sCluster` (`k8s_handlers.go:75,97`) | CORE |
| `TunnexExposedService` | `exposeK8sService` / `unexposeK8sService` (`k8s_handlers.go:138,163`) | CORE |
| `TunnexGrant` | `createPolicyRule` (`dst_kind=k8s_service`) / `deletePolicyRule` (`policy_handlers.go:272,314`) | ENTERPRISE |

## Decide-items — RULED

### D1 — CRD set: ALL THREE. RULED.

Ship `TunnexCluster` + `TunnexExposedService` + `TunnexGrant`; retire `TunnexPeer`/`TunnexRoute`. **The full
set, not a subset:** `TunnexGrant` is what makes this GitOps rather than a partial view — a platform team
that can declare a cluster and a service but must click a dashboard to grant access has a broken workflow.
The CP already gates `TunnexGrant` correctly by edition (D6), so shipping it costs no new gate. Rejected:
cluster+service-only (grant later) — it ships a knowingly-broken GitOps story.

### D2 — Direction of authority: (A) CRD source-of-truth, SCOPED BY OWNERSHIP. RULED.

The operator reconciles the CP to match the CR **for objects the operator owns**. This is honest, not a
contradiction of "the CP is the one truth": **the CP remains the one truth about STATE; a CR is a
declaration of INTENT for objects the operator owns.** Dashboard-created objects have NO CR and are
**untouched** (no owner-ref → not managed). Conditions (all three are build requirements):

1. **Ownership is EXPLICIT and VISIBLE** — a label/owner-ref the CP can surface, so the dashboard shows an
   object as operator-managed and **warns or refuses** on a manual edit: "this Service is managed by GitOps
   — edit the CR." **Silently reverting an admin's dashboard change on the next reconcile is the worst
   possible UX** — the honest form surfaces the ownership AT THE POINT OF EDITING. This is the render-floor
   discipline applied to authority.
2. **Delete-CR-deletes-the-object, AUDITED with cascade counts** — a `kubectl delete tunnexcluster prod`
   that cascades away grants with no forensic row is governance vanishing untraceably (the S10.3 H2 lesson
   exactly). The audit row names **the CR as the cause**. Inherited by construction *iff* the delete routes
   through `deregisterK8sCluster` (which already captures `services_deleted`+`grants_deleted`,
   `k8s/service.go:383-391`) — never a DB delete (the hard rule).
3. **Drift surfaces in CR STATUS, not just logs** — and per D7's caution, status reflects **CP acceptance**,
   never merely "applied" (see honest-health below).

Rejected: (B) CRD-as-projection (CP truth, CR reflects) — dashboard would win and the CR would be a
read-only mirror; that is not GitOps (you cannot manage state from git if the CP overrides), a weak value
prop.

### D3 — Operator identity to the CP: (ii) a first-class MACHINE PRINCIPAL. RULED.

Verify found there is **no machine principal today** — the only org-API credential is the `tnx_` bearer,
which is **user-bound** (bearer ≡ session = a user, `bearer.go:26,61`); agents authenticate by mTLS on a
SEPARATE channel that does not expose the org-management verbs (`agentchannel.go`). Ruling: a **machine
principal**, because (i) a service-user `tnx_` token makes every GitOps change **look like a human did it**,
corrupting the one question the audit trail exists to answer ("who changed this, and why"). This product has
twice ruled that system actors carry distinguishable identity with a cause (idp-sync, device-health, policy
grant-expiry). An operator impersonating a service-user is **the swallowed-audit law's cousin — the row
exists but attributes falsely, which is worse than absent because it is confidently wrong.**

Conditions:
- **First-class org credential, NOT a user-with-a-flag.** No `is_machine` boolean on `users` — that would
  put a non-human in the identity-binding invariant's SUBJECT space, and **D4 ruled workloads out of that
  space.** A separate machine-principal entity.
- **Scoped to what the operator needs** — org-scoped, the same RBAC verbs it would use (`k8s:manage`,
  `policy:manage`).
- **Revocable independently; revocation severs immediately.**
- **Minted through a one-time ceremony** like every other credential; **fingerprint-only in audit** (never
  the secret).
- **Audit attribution = `actor_system`** (a distinguishable operator/machine actor) **with the CR as the
  cause**, per the existing `writeSystemAudit` convention (`tenancy/service.go:212`).

**COST FLAG (surfaced, per the founder's instruction — do not absorb silently):** a new credential primitive
touches auth (mint/verify), RBAC (the principal's role binding), audit (a non-user actor flowing into the
mutation audit path — today every K8s mutation audits `ActorUserID`, `k8s/service.go:94`), and the
mint/revoke surface. This is the **largest net-new piece** of S10.2. The commit-one build sketch below scopes
it as **Slice 1**; if, on building it out, it proves **larger than a contained slice** (e.g. it forces a
rework of the `Principal`/audit types across many handlers), that is surfaced BEFORE building further and we
decide whether it is S10.2's first slice or **its own small story that S10.2 stacks on**.

### D4 — Reuse of the S3.1 reconcile design: CONFIRMED (clarified).

"Reuse the DESIGN" = **re-declare the DECISION policies**, not copy the WG/nft data-plane loop (verify's
portable-vs-specific split):
- **Free from controller-runtime:** dual-trigger (informer watch + `SyncPeriod` resync — reconcile.go's
  Watch+ticker) and full-resync / level-triggered idempotent Reconcile.
- **Re-declared (portable logic):** **keep-last-on-CP-error** — a CP-API error NEVER deletes or mutates the
  CR's managed object (the `runOnce` "fetch error returned WITHOUT touching the backend" property,
  `reconcile.go:310`); **fail-static** — hold last-good, surface drift, never revert to a permissive/empty
  state (`egress_linux.go:257` refuse-not-fall-to-mesh).
- **New (does NOT port):** the atomic-apply MECHANISM. The agent gets all-or-nothing from `nft -f -` /
  `wg syncconf`; the operator gets **per-object** atomicity from the CP API, not one transaction across the
  desired set — so a multi-object CR reconcile needs its own ordering/rollback story (create-before-grant;
  on partial failure, leave the succeeded objects + a non-Ready status naming what failed, never a partial
  silent success).

### D5 — Module + RBAC discipline: CONFIRMED.

New Go module **`apps/operator`** (controller-runtime + client-go). Own `go.mod`; `GOFLAGS=-mod=readonly` +
the module-path GUARD note (module path `github.com/tunnexio/tunnex/...` ≠ repo, per every other module's
guard); a both-editions build guard for whatever CP client types it shares (it builds edition-agnostic — the
edition gate lives at the CP, D6). The operator's **own cluster RBAC** (stated in the security posture beside
the gateway's read-only services/endpointslices grant): `get/list/watch` + `status` update on its **three
CRDs ONLY** — it needs NOTHING else in-cluster (no services, no endpointslices, no secrets beyond its own CP
credential Secret). Posture sentence: "the operator watches its own TunnexCluster/TunnexExposedService/
TunnexGrant CRs and calls the Tunnex control plane over HTTPS with a machine credential; it reads no other
cluster resource, and holds no data-plane privilege."

### D6 — Edition line: CONFIRMED.

The operator **binary is open** deployment tooling. `TunnexGrant` gates **`edition_required` (403) at the CP
by construction** — it calls `createPolicyRule`, which returns `policyEditionRequired()` in the open build
(`policy_handlers.go:275`). `TunnexCluster`/`TunnexExposedService` are CORE (connectivity, `k8s_handlers.go`
has no edition check). **No build-tag gating in the operator** — the CP enforces; the operator surfaces the
403 honestly in the CR status (a `TunnexGrant` applied against an open-edition org → CR status names
`edition_required`, never a silent no-op).

### D7 — Ledgered bindings: CONFIRMED (see THE HARD RULE at top).

All inherited **by construction via the API-client design**, and only while it holds:
- **Collect/OrgRanges law** — a `TunnexCluster` create hits `registerK8sCluster` → `subnetguard.Collect`
  (`k8s/service.go:151`); the operator can NEVER hand-build an `OrgRanges` (it does not import the package).
- **Identity-binding** — `TunnexExposedService` is a DESTINATION (stable id, not a subject —
  `docs/S10.3-decisions.md:48`); `TunnexGrant`'s subject ∈ {user, group, site, cidr}; **no workload subject,
  no `TunnexPeer`** (an unowned/workload peer is D4-ruled-out).
- **Edition gate** — inherited (D6).
- **H2 audit-with-cascade-counts** — inherited (D2 condition 2) *iff* deletes route through the audited API
  verbs.
- **Zero-config golden** — unaffected: the operator adds no compiled-artifact field; it drives existing
  verbs only.
- **Honest-health / ARTIFACT-EXISTS ≠ ARTIFACT-WORKS** (the epic's thrice-named trap — WF-OVPN-1, H1, WF-K5,
  `docs/S10.3-decisions.md:546`): a CR that reconciles green is NOT proof the grant took effect. **CR status
  MUST reflect the CP's actual acceptance** (the API response — created id / 4xx code), and where feasible
  the downstream reality, never merely "I sent the request." The status red asserts a CP 4xx becomes a
  non-Ready CR condition naming the CP error code, not a green Ready.

## Proposed slice cut (BUILD PLAN — pending sign-off; nothing built yet)

Decision-first; the machine principal is first so the cost flag (D3) is resolved before the CRD layer leans
on it.

- **Slice 1 — the machine principal (CP-side, the cost-flagged piece).** A first-class org machine credential
  (mint one-time, verify, revoke-severs-now, org-scoped RBAC, fingerprint-in-audit) + `actor_system`
  attribution flowing into the K8s/policy mutation audit path with a cause. **HALT-GATE (armed) — the
  tripwire is ADDITIVE vs INVASIVE:** a new PRINCIPAL KIND that flows through the EXISTING `Principal`/auth
  plumbing (existing types absorb it; attribution branches only in the ~6 operator-driven mutation handlers)
  is a SLICE — proceed. A REWORKED principal MODEL (the `Principal`/auth types change shape across many
  handlers) is its OWN STORY that S10.2 stacks on — HALT and surface. **Surface the judgement either way;
  never decide it silently.** The assessment runs BEFORE the deep build. Reds: mint→use→revoke→denied; an
  operator-driven mutation audits `actor_system` + cause, never a user id.
- **Slice 2 — the CRD schemas + `apps/operator` skeleton.** Three CRDs (TunnexCluster / TunnexExposedService
  / TunnexGrant) + controller-runtime manager; the generated CP HTTP client; the census RED (no DB import).
  No reconcile logic yet — schemas + the client + the module guards + both-editions build. **CONDITION (the
  schemas are the customer-facing contract, hardest to change later):** the CR **spec** fields MIRROR the
  API's own vocabulary — the SAME nouns the dashboard + docs use (`protocol`, `port`, `namespace`, `service`,
  and the S10.3 FQDN naming ruling `<service>.<namespace>.svc.<cluster>.<zone>`) — so a platform engineer
  reading a CR and an admin reading the dashboard see ONE product. The **resolvable FQDN goes in the CR
  STATUS, not spec** — it is DERIVED (server-built, `k8s/service.go:266`), and status is where derived truth
  belongs (never client-constructed — the S10.3 copy-don't-construct naming ruling).
- **Slice 3 — reconcile (create/update path).** CR → API call → status; keep-last-on-CP-error, fail-static,
  ownership label/owner-ref, honest status (CP 4xx → non-Ready naming the code). The ordering/rollback story
  for a multi-object reconcile (create-before-grant).
- **Slice 4 — delete + drift.** Finalizer → routes delete through the audited API verb (cascade counts, CR
  as cause); the dashboard-side ownership surface (managed-badge + warn/refuse manual edit — D2 condition 1);
  drift detection → CR status.
- **Slice 5 — review + box-walk.** Story-end multi-finder review; a live GitOps walk. **The walk's teeth,
  at FULL STRENGTH (ARTIFACT-WORKS applied to GitOps):** the proof is NOT "kubectl apply and the CR goes
  Ready." It is a **declared `TunnexGrant` ADMITTING a real flow on the wire that was DENIED before it** —
  the exact WF-K6 shape (deny → allow → revoke with drop/accept counter evidence), driven from **YAML instead
  of the dashboard**. And the inverse: **`kubectl delete` the grant → the flow DIES** (revocation on the
  wire, cascade audited). Anything short of a flow that flips deny→allow→deny under `kubectl apply/delete`
  proves the CR reconciled, NOT that GitOps governs. Plus: the ownership surface (edit-in-dashboard warns,
  not silent-revert) and the delete-cascade audit (counts + CR as cause) proven live.

Registered residuals to carry (not S10.2 scope): workload-as-source-identity (D4, ruled out of EPIC 10 —
the only thing that would revive a `TunnexPeer`); sub-tick authoritative-ClusterIP (superseded by WF-K5).

## Slice 1 build conditions (ruled)

- **Mint = the full one-time-secret discipline** (join-token / WG-config / .ovpn parity): the `tnxm_` token is
  shown EXACTLY ONCE at mint, the list + audit carry the KEYED FINGERPRINT only, there is NO route that
  re-renders the secret, an "I've saved this" acknowledgement gates dismissal, and the LOSS PATH is stated:
  **revoke and re-mint, never re-display.** RED: no code path re-renders the secret.
- **`PermMachineManage` is OWNER-ONLY, and the reasoning is on the record:** minting a machine credential
  with `policy:manage` creates a non-human actor that can **rewrite access policy** — that is org-delete-grade
  privilege, so it sits with the owner, never admin. (Stated at `rbac.go` PermMachineManage + here.)
- **The audit branch is the slice's SUBSTANCE, not its trim** — it is what makes D3 real. The RED asserts the
  NEGATIVE as well as the positive: a machine-driven mutation writes `actor_system` (`operator:<name>`) +
  cause and **NEVER a user id**, so a future refactor cannot quietly re-attribute operator changes to a human
  (the confidently-wrong-attribution failure D3 exists to prevent).

## Held findings (surfaced, not folded)

### F-3a-1 — the three CREATE paths don't audit at all. HELD.

Threading `managed_by_machine` through `RegisterCluster` / `ExposeService` / `CreatePolicyRule` (Slice 3a)
made conspicuous that these three creates emit **no audit row at all** — not for a human, not for a machine.
Deletes DO audit (`DeregisterCluster` / `UnexposeService` route through `AuditActor()` → system-vs-user
branch, wired in Slice 1); the creates never did. So a machine (or human) standing up a cluster/service/grant
leaves an ownership MARKER but no audit CAUSE. Per the ruling this is NOTED as a finding, not silently fixed:
the marker (`managed_by_machine`) records WHO owns the row for the Slice-4 dashboard; a create-audit row would
record WHO+WHEN+CAUSE created it. They are different obligations. Fix candidate = mint create-audit in all
three services keyed off the same `AuditActor()` seam the deletes use (machine → `actor_system` + cause,
human → `actor_user_id`). Disposition at Slice-3 review or a named follow-up; do not absorb into 3a.

The marker is **nullable and inert** for dashboard-created objects: `uuid.Nil` → `managed_by_machine` NULL,
zero behavior change (goldens/reds assert the NULL). It is recorded now only so the Slice-4 ownership surface
never retrofits live rows.

## Slice 3b build notes (the three reconcilers)

Built: `internal/controllers` — one reconciler per CRD, each a `*cp.Client` holder (THE HARD RULE: no DB
handle in the binary — the `TestNoDBImport` census still passes with controllers + controller-runtime added).

- **Honest status** — a CR is `Ready=True` ONLY on a CP 2xx. A CP **4xx** (`onCPError`) becomes
  `Ready=False` naming the CP's own `code` + `message` VERBATIM (e.g. `invalid_vip_range`, `edition_required`,
  `subject_not_found`); a bad spec is not a controller error (returns nil, slow-requeues). A CP **5xx /
  transport** failure is **keep-last / fail-static** — status UNTOUCHED, the error is returned so
  controller-runtime backs off. Reds assert both halves per reconciler.
- **Requeue ordering** — service waits on its cluster's `status.ClusterID`, grant waits on its service's
  `status.ServiceID`; each requeues (`requeueDependency`) until the dependency's status is populated. No
  topological sort — the ordering FALLS OUT of the status dependency. Reds: `TestServiceWaitsForCluster`,
  `TestGrantWaitsForService` (CP is a `cpDown` that fails if touched — proves no premature call).
- **Ownership** — the AUTHORITATIVE record is CP-side `managed_by_machine` (Slice 3a), stamped because the
  operator authenticates with its `tnxm_` machine credential. The reconcilers ALSO stamp a k8s-side
  `tunnex.io/managed-by=operator` label (first pass labels + requeues, before any CP contact —
  `TestOwnershipLabelStampedBeforeCP`) for kubectl / the Slice-4 dashboard surface.

**Resolved design point (obvious default, no fork surfaced):** the CRDs carry FRIENDLY subjects/refs — a site
NAME, a user EMAIL, a group NAME — but the CP mutation verbs want UUIDs. Resolution wires the EXISTING
read-only GETs (`/sites`, `/members`, `/groups`) client-side; a name that doesn't resolve is an HONEST
`Ready=False` (`site_not_found` / `subject_not_found`), a transport failure is keep-last. No new CP surface —
the operator stays a pure API CLIENT.

**Residuals registered (not 3b scope):**
- **R-3b-1 (grant idempotency):** policy rules aren't named and there's no list-find, so grant idempotency
  rests on `status.RuleID`. A create-then-status-write failure could double-place a rule; identical grants are
  same-effect (default-deny + idempotent allow). Reconcile against duplicates lands in **Slice 4 (drift)**.
- **R-3b-2 (watch vs poll ordering):** dependency ordering is requeue-polled, not `Watches`-driven — a
  service/grant wakes on a timer after its cluster/service goes Ready, not instantly. A `Watches`+enqueue-
  dependents refinement is a Slice-4/later nicety; polling is correct, just not instant.
