# S15.2 — the address-bearing agent, and the agent as a principal

**Commit-one. Paper before product code.** Branch `story/S15.2-address-bearing-agent`.

**RULED BY THE FOUNDER: ONE STORY, D15 THEN D4.**

The reason is an asymmetry, recorded as the reason and not as a preference:

> ## **D4-THEN-D15 SHIPS A ROLE THAT NAMES NOTHING FOR THE LENGTH OF THE GAP. D15-THEN-D4 HAS NO MIRROR
> ## PROBLEM.** Attribution is what a role is *for*; a role that predates the thing it attributes is inert.
> ## The reverse order costs nothing, so the ordering is not free and the story is not splittable at zero cost.

⚠ **And it is stronger than "inert".** D4 alone would add a role **nothing can be minted with** — the machine
role is hardcoded at mint (`machineauth/service.go:85`) and agents hold no machine credential at all.

## 0. THE FRAMING THAT WAS RETIRED BEFORE THIS PAPER WAS WRITTEN

A check was ordered before the cut: *does narrowing the machine role independently close register item #1
(`operator` holds `PermPolicyManage`), making it a security fix that merely shares a slice?*

**It does not, and both the founder and I had under-read the register entry.**

`PermPolicyManage` gates **all ten** policy-write handlers — `policy_handlers.go:81, 98, 115, 148, 164, 197,
214, 231, 272, 315`. **Reconciling `TunnexGrant` CRs into policy rules is the GitOps operator's entire job.**
Removing the perm does not narrow the operator; it breaks it.

The register entry already said so in its own words — *"the same grant is correct for a GitOps operator and
inverts the threat model for an agent"* — and that sentence is the whole answer.

> ## **THE FIX IS NOT "REMOVE `PermPolicyManage`". IT IS "STOP HAVING ONE ROLE FOR TWO PRINCIPAL KINDS", AND
> ## IT CANNOT SHIP BEFORE THE SECOND KIND DOES.** So no security fix leads this story. The ranking is the
> ## ruled ordering, unmodified.

Supporting measurements, so this is not re-litigated:

| claim | measured |
| --- | --- |
| `operator` is unreachable by a human | `CHECK (role IN ('owner','admin','member'))` — `0002_tenancy.up.sql:48` |
| every non-test `RoleOperator` reference | **two**: `rbac.go:84,137` and `machineauth/service.go:85` |
| an agent holds a machine credential | **no** — zero references in `apps/node`; enrolment never touches the table |
| anything branches on the machine role | **no** — `AuthMachine` has one non-test reference, and it is a comment (`handlers.go:73`) |

## 1. D15 — THE AGENT IS ADDRESS-BEARING (ruled at S15.0; the binding, restated with its cost)

**Binding, not preference.** Attribution rides the artifact's `/32`→device map
(`accesslog/ingest.go:40-75`).

> ## ⛔ **A PRINCIPAL DESIGN THAT AVOIDS THE `/32` GOES DARK ON ATTRIBUTION, SILENTLY, AND THE FLOW LOG WILL
> ## NOT COMPLAIN.** There is no error, no gap, no warning — the events simply resolve to nothing and the
> ## screen renders an emptier truth than the truth.

### The cost, already measured at S15.0 and carried here rather than re-derived

Every agent takes **one address from the org pool**. `organizations.pool_cidr` defaults to **`10.99.0.0/24`**
— a hardcoded column default — and `ipalloc.go` reserves network, gateway and broadcast, leaving **253
allocatable addresses, org-wide, shared with every human's devices.** Exhaustion is a hard refusal
(`pool_exhausted`, `devices/service.go:296`).

⚠ **Each agent is within the per-user cap and the fleet collectively exhausts a shared pool** — the same
org-pool DoS the cap convention was written against (`devices.sql:100-101`), arriving through a door the cap
does not watch.

⛔ **AND NOTHING SURFACES POOL UTILISATION.** D16 ruled the pool is *not a ceiling* — it is resizable
(`organizations.sql:56`), the resize has a UI (`Settings.tsx:407-435`), and S4.5b's grow-superset path with
its orphan check is proven. **But resizable-and-invisible means the first signal is the refusal.** Registered
separately at S15.0; **not built, and this story does not build it.** Named here so the cost is not recorded
as mitigated.

## 2. D4 — RE-MEASURED. THE OLD NUMBER ANSWERED A DIFFERENT QUESTION.

**D4 MEANS: AGENTS BECOME RBAC PRINCIPALS.** Founder-ruled. Not a narrower role on a credential they do not
hold.

**The reason is EPIC 15's own thesis:** an agent is a non-human principal that acts unattended, and the epic
exists to bound its blast radius.

> ## ⛔ **A THING THAT AUTHENTICATES BUT IS NEVER AUTHORIZED HAS NO BLAST RADIUS TO BOUND.** Shipping the
> ## narrower role without the principal would ship the epic's name with none of its content.

### What agents actually are today — measured

| question | answer | citation |
| --- | --- | --- |
| does the agent channel build an `authctx.Principal`? | **No** | `agentchannel.go` — **zero** `authorize(` / `authctx.` references |
| what authenticates an agent? | a **client-cert serial** → a `sqlc.Node` row | `agentchannel.go:84-86`; `nodes/service.go:315-323` |
| what is passed downstream? | `node.OrgID, node.ID` — raw ids | `agentchannel.go:103` |
| principal constructors in `authctx` | **one** — `NewMachinePrincipal` | `authctx.go:86` |

**Agents are authenticated and never authorized.** mTLS, cert-serial lookup, status check — then raw ids. They
live entirely outside the principal/RBAC system.

### ⛔ THE S15.0 BLAST RADIUS IS STRUCK, NOT EDITED AWAY

S15.0 recorded: *one grant-table entry, one mint site, one regenerate, two test updates, no spec change.*
**That number is correct and it measured the cost of ADDING a role to the table.** It did not measure the cost
of **agents holding one**.

⚠ **The condition it recorded was the right instinct on the wrong axis.** *"Cheap BECAUSE machine roles are
not user-assignable"* guards against assignability. What makes D4 expensive is that **the principal does not
exist.**

**The real shape:** an agent principal · an `AuthAgent` method · `authorize()` on routes that have never
called it · and the census question in §4.

> ## **AN UNDER-MEASUREMENT, NOT AN ERROR — AND THAT DISTINCTION IS WHY THE OLD LINE IS STRUCK IN PLACE ON
> ## `main` RATHER THAN DELETED.** The record that the number was tested is worth more than a clean line.

## 3. DOES AN AGENT GET AN OWNER? — ANSWERED HERE, NOT DISCOVERED IN A SLICE

**D14 ruled owned principals. An ownerless agent principal would re-open exactly what S15.1 closed.**

⛔ **AND D14'S SEAM DOES NOT COVER AGENTS — MEASURED, NOT ASSUMED.** S15.1 put `user_id` on
`machine_credentials`. Agent enrolment **never touches that table** (zero references in `nodes/`,
`agentca/`), so an agent inherits **nothing** from S15.1.

**What exists today:**

| table | owner column | citation |
| --- | --- | --- |
| `devices` | **`user_id uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE`** — *"owner; no unowned peers"* | `0010_devices.up.sql:11` |
| `nodes` | **none** — `org_id` only | `0008_nodes.up.sql:19-31` |
| `node_join_tokens` | **none** — `org_id`, `node_name`, `token_hash`, `expires_at`, `consumed_at`, `consumed_node_id`, `created_at` | `0008_nodes.up.sql:39-48` |

⭐ **AND THE ISSUER IS KNOWN AND THEN DISCARDED.** `IssueJoinToken(ctx, actor, orgID, nodeName)` takes the
human as `actor` (`nodes/service.go:234`) and `CreateJoinTokenParams` carries **`OrgID, NodeName, TokenHash,
ExpiresAt`** — no actor column. **The human is written to the audit log and to nothing else.**

> ## **THE ATTRIBUTION FACT EXISTS AT EXACTLY THE MOMENT IT IS THROWN AWAY.** The person who authorized this
> ## agent into the org is known, in-hand, at issue time — and is preserved only in a log nobody joins
> ## against. That is the same shape as S15.1's finding, one table over.

**DECIDE-ITEM (held): where does an agent's owner come from?** Three shapes, none picked:

1. **the join-token issuer**, carried through enrolment onto the node — the fact already exists and is
   discarded; ⚠ but a token can be minted by one admin and redeemed weeks later by another operator, so
   *issuer* and *installer* are not the same person and the paper must not conflate them.
2. **assigned after enrolment**, exactly as S15.1's screen does — consistent, and it reproduces S15.1's
   refusal problem: an agent refused until someone assigns it is a gateway that will not come up.
3. **an org-level service owner** — one accountable human for all agents; cheapest, weakest.

⛔ **Not resolved here. The founder rules it.** ⚠ What the paper *does* record: **option 2's refusal
semantics are not free.** S15.1 could refuse an unowned credential because a refused GitOps operator fails a
pipeline. **A refused agent fails a data plane** — and EPIC 13 exists because a gateway that cannot come back
is the worst failure this product has.

## 4. IS AN AGENT A DEVICE ROW, OR ITS OWN KIND? — gifts and costs, stated separately

**If an agent is a `devices` row it inherits, and the inheritance cuts both ways.**

**GIFTS**

- **attribution** — it lands in the `/32`→device map with no new machinery. This is D15 satisfied *by
  construction* rather than by a parallel implementation.
- **revocation full-sweep** — the established invariant (peer slot + pool address + telemetry) applies
  unchanged, and no second sweep path can drift from the first.
- **the delegation link and provenance** already hang off `devices.user_id`.

**COSTS**

- **`CountDevicesForUserCap`** counts `active` + `pending` (`devices.sql:100-101`). ⛔ **Every agent an admin
  enrols would spend that admin's personal device cap** — a fleet of gateways charged to one human's laptop
  allowance. The convention is right for humans and wrong here.
- **a pool address each**, against 253 org-wide (§1).
- ⚠ **`devices.user_id` is `ON DELETE CASCADE`, and `machine_credentials.user_id` is `ON DELETE RESTRICT`** —
  S15.1 chose RESTRICT deliberately, against the S14.12 cascade class. **If an agent is a device, deleting a
  user silently deletes their agents**, which is the S14.12 finding arriving through a door S15.1 already
  closed one door down. **The two tables would disagree about what an owner's deletion means.**

⛔ **HELD, NOT PICKED.** ⚠ And the honest note: the gifts are *large* — attribution and revocation are the two
hardest things in this epic and both come free — while every cost has a named, bounded fix (exempt agents from
the cap; resize the pool; align the FK action). **That asymmetry is an argument, not a decision.**

## 5. D24 — WHERE IS THE AGENT PRINCIPAL CONSTRUCTED? **SURFACED, NOT RESOLVED.**

⛔ **THE S15.0 CENSUS LICENSED A CONSTRUCTOR BECAUSE `MachineID` HAD EXACTLY ONE CONSTRUCTION SITE.** A second
principal kind entering by a different door **reopens the question the census closed**.

The census's own recorded caveat is the governing sentence: *the constructor was licensed by the census, not
by the pattern* — and `policyHealthBadge` is the counter-example, where seven sites existed and four were
wrong, two of which never called the function at all.

**Two shapes, both held:**

| shape | what it preserves | what it costs |
| --- | --- | --- |
| **one constructor, principal-kind discriminator** | the one-site property survives; the census stays true | couples two unrelated auth paths (bearer token and mTLS) through one signature |
| **a second constructor** | each auth path stays legible on its own terms | ⛔ the census must be **RE-RUN** and "necessary AND sufficient" **RE-ARGUED for both** — it does not carry over |

⛔ **WHAT IS NOT ACCEPTABLE IS A SECOND SITE ADDED QUIETLY.**

> ## **THE PROPERTY WAS MEASURED ONCE AND IS NOT SELF-RENEWING.** A census is a statement about a moment. Code
> ## added after it is not covered by it, and the second site would be exactly the kind of addition that looks
> ## like it inherits a guarantee it was never inside.

## 5A. D25 — WHAT HAPPENS WHEN AN AGENT PRINCIPAL HAS NO OWNER, OR ITS OWNER IS DEACTIVATED?
## **SURFACED AND HELD. THIS IS THE ITEM THAT DECIDES §7.**

⛔ **D14'S REFUSAL PATTERN CANNOT BE COPIED ONTO AGENTS WITHOUT A RULING.** §3 records that refusal semantics
"are not free"; that sentence was left as an observation and it is actually a decide-item, which is why it is
now one.

### The asymmetry, stated plainly

> ## **S15.1'S REFUSAL WAS CHEAP BECAUSE THE THING IT BROKE WAS RECOVERABLE IN MINUTES BY A HUMAN AT A
> ## SCREEN.** An owner-less GitOps operator fails a pipeline; an admin opens Settings, picks a name, and the
> ## pipeline runs again. **An agent's refusal is not that.** It takes down a tunnel, for an
> ## identity-management reason, and the human who could fix it may be on the far side of the tunnel.

⚠ **AND THIS PRODUCT HAS ALREADY PAID FOR THAT CLASS ONCE.** EPIC 13 exists for one observed event — an AWS
gateway went offline past its cert lifetime and could not come back. **A gateway that cannot come back is
this product's worst failure**, and the fail-closed cold-start limitation (`PLAN.md:823-832`, S7.2,
`TestNeverReceivedIsDenyAllNotMesh`) is already a **named and accepted** availability cost. D25 would add a
second, from a different cause, to the same component.

⛔ **Note the difference between them, because it is what makes D25 harder:** cold-start deny-until-first-fetch
is a **security** fail-closed — the alternative is a reboot-during-outage turning an enforcing org into an
open mesh, which is a breach. **An identity-management refusal has no equivalent breach on the other side.**
An unattributable tunnel is a *logging* failure, not an *access-control* one — the policy engine still
enforces every rule.

### Three shapes. **None picked.**

| shape | what it buys | what it costs |
| --- | --- | --- |
| **1 — refuse at use** (S15.1's symmetry) | one rule for all non-human principals; the invariant holds continuously and cannot decay | ⛔ a tunnel drops for an identity reason. Deactivating an offboarded admin takes down every gateway they enrolled — **D23's cost, arriving on the data plane instead of a pipeline** |
| **2 — refuse at ENROLMENT, never at use** | an owned agent is *required to exist*; an already-running agent keeps running. **No new outage class.** The invariant holds for every agent created after the change | ⚠ it decays exactly as D21 does: owned when written, unowned later, with nothing catching it. And it needs an answer for agents enrolled **before** the change |
| **3 — degrade, do not refuse** | it runs, it is **flagged**, and it declares itself unattributable | the honest-state option, and the one that says the quiet part: **attribution is best-effort.** ⚠ A flag nobody reads is the reassuring-empty class — it only works if the degraded state is surfaced where an operator already looks |

⚠ **AND THE THREE ARE NOT MUTUALLY EXCLUSIVE.** 2+3 compose: refuse at enrolment, degrade-and-flag for the
decay case. That combination is *not* a recommendation — it is a note that the ruling need not be one of
three.

### What this shares with D23, and where it diverges

D23 asks the same question of **machine credentials** and is already held. ⛔ **They should probably be ruled
together, and the paper will not assume it** — the answers can legitimately differ, because the blast radius
differs by exactly the distance between a pipeline and a data plane. **Naming them as one item would smuggle
that difference away.**

## 7. DECIDE-ITEMS FOR THE FOUNDER — one block each, ranked by what blocks what

⛔ **NOTHING BELOW IS RESOLVED. NO PRODUCT CODE UNTIL THEY ARE DISPOSITIONED.**

⚠ **FIRST: TWO OF THESE WERE ONE QUESTION WEARING TWO NAMES.** The original §7 listed *"where does an agent's
owner come from"* and *"what happens to a gateway refused for want of an owner"* as separate items. **The
second is D25 and it SUBSUMES nothing — it GOVERNS.** They are now one ranked chain rather than two votes:
D25 decides whether ownership is an availability dependency at all, and only then does the source matter.
**Merging saved a ruling; it did not save a question.**

---

### ⛔ D25 — RANK 1. BLOCKS EVERYTHING BELOW.

**THE QUESTION:** When an agent principal has no owner, or its owner is deactivated, does the agent
**(A)** stop authenticating at use, **(B)** stay running but be refused at *enrolment* so it could never have
existed unowned, or **(C)** keep running, flagged, declaring itself unattributable?

**RECOMMENDATION: B, composed with C** — refuse at enrolment so no unowned agent is ever created, and
degrade-and-flag for the decay case (owner deactivated later), never dropping a live tunnel.

**IF RULED THE OTHER WAY (A):** deactivating one offboarded admin takes down every gateway they enrolled, at
that moment, with no warning — D23's cost arriving on the data plane instead of a pipeline, in a product
whose worst observed failure is a gateway that cannot come back.

⛔ **WHAT CANNOT BE DECIDED LATER:** **the enrolment refusal.** Refusing at enrolment is free *before* any
agent enrols under the new schema and becomes a **backfill** afterwards — the exact expand/contract problem
S15.1 is still living through, whose step 4 (`NOT NULL`) is *not yet done and has no date*. Choosing A or C
now and B later means retrofitting owners onto a running fleet. **Choosing B now costs one `NOT NULL` at
creation.** ⚠ The reverse is not symmetric: B→C later is a relaxation and is cheap.

---

### ⛔ RANK 2 — WHERE DOES AN AGENT'S OWNER COME FROM? *(only matters once D25 is ruled)*

**THE QUESTION:** Is an agent's owner **(A)** the human who issued the join token, captured at issue,
**(B)** assigned after enrolment through a screen, or **(C)** a single org-level service owner?

**RECOMMENDATION: A, reassignable by B's screen.** ⚠ **Because it is the only fact that exists at a moment a
human is present.** Enrolment is an agent redeeming a token unattended — **the installer is not capturable at
all, by construction**, which is why the paper refuses to conflate issuer with installer and why C exists as
the fallback rather than as a third peer.

**IF RULED THE OTHER WAY:** B alone means every agent is unowned between enrolment and someone noticing —
under D25(A) that is a gateway that never comes up. C alone re-creates the ownerless principal D14 ended,
wearing an org's name instead of nobody's.

⛔ **WHAT CANNOT BE DECIDED LATER — AND THIS ONE IS LOSING DATA RIGHT NOW:** `node_join_tokens` has **no
issuer column** (`0008_nodes.up.sql:39-48`), and `IssueJoinToken` takes the human as `actor` and writes them
**to the audit log and nowhere else** (`nodes/service.go:234`). **Every join token minted between now and the
ruling loses its issuer to a table nobody joins against.** Adding `issued_by` is one nullable column today;
after the fact the history is **unrecoverable except by parsing audit metadata**. ⚠ This is the only item on
the list with a running cost.

---

### ⛔ RANK 3 — IS AN AGENT A `devices` ROW, OR ITS OWN KIND?

**THE QUESTION:** Does an agent principal reuse the `devices` table — **(A)** yes, **(B)** no, its own kind?

**RECOMMENDATION: A**, with the per-user cap explicitly exempted for agent rows. The gifts are the two
hardest things in this epic and both come free: **attribution by construction** (it lands in the
`/32`→device map with no parallel implementation) and **the revocation full-sweep** (peer slot + pool address
+ telemetry) with no second sweep path that can drift.

**IF RULED THE OTHER WAY (B):** every one of those is re-implemented, and the second implementation of a
sweep is the class this repo has already paid for — *one-truth*, five recorded instances.

⛔ **WHAT CANNOT BE DECIDED LATER:** **the table.** A/B is a schema commitment that binds attribution,
revocation, the cap and pool allocation simultaneously; reversing it after agents exist is a data migration
plus a period where both paths are live. **Everything else in this block is a tunable; this is the one that
is not.**

⛔ **AND THE FK DISAGREEMENT MUST BE RULED WITH IT, NOT AFTER:** `devices.user_id` is **`ON DELETE CASCADE`**
(`0010_devices.up.sql:11`); `machine_credentials.user_id` is **`ON DELETE RESTRICT`**, chosen deliberately at
S15.1 against the S14.12 cascade class.

> ## **THE TWO TABLES ARE NOT PERMITTED TO DISAGREE ABOUT WHAT AN OWNER'S DELETION MEANS.** One says *deleting
> ## a user silently deletes what they owned*; the other says *deleting a user is refused while they own
> ## anything*. Both are defensible; **holding both is not a position, it is an accident** — and under
> ## option A an agent inherits whichever one it lands next to.

⚠ **The direction is not neutral and the paper will not pretend it is:** RESTRICT is the S15.1 ruling and
CASCADE is the S14.12 defect class, so **`devices` is the one out of step.** But changing a long-shipped FK
on the devices table is **not S15.2's scope** — it is registered here so the divergence is a *known* one
being carried deliberately, not one discovered later by whoever deletes a user.

### ⛔ RANK 4 — D24: WHERE IS THE AGENT PRINCIPAL CONSTRUCTED?

**THE QUESTION:** **(A)** one constructor with a principal-kind discriminator, or **(B)** a second
constructor, with the census re-run and "necessary AND sufficient" re-argued for both?

**RECOMMENDATION: B, with the census re-run as a gate on the slice** — not A. Coupling a bearer-token path
and an mTLS path through one signature to preserve a *counting* property trades a real coupling for a
bookkeeping one.

**IF RULED THE OTHER WAY (A):** two unrelated auth paths change together forever, and the discriminator
becomes the thing every future principal kind must be threaded through.

⛔ **WHAT CANNOT BE DECIDED LATER — AND THE HONEST ANSWER TO THE QUESTION AS ASKED:**

**A SECOND PRINCIPAL KIND RETIRES THE PROPERTY. It does not preserve it.** The S15.0 census established that
**`MachineID` has exactly one construction site** (`http/machine_bearer.go:43`), which is *why* a constructor
was licensed there rather than a per-handler guard. Strictly, adding an agent principal with its own id field
leaves that `MachineID` sentence true — **and the guarantee it was standing in for does not survive**, because
the guarantee was never about `MachineID`. It was: *a non-human principal cannot be built without passing
through the one place that enforces ownership.* **A second kind with its own field has its own doorway, and
the old census says nothing about it.**

**WHAT REPLACES THE GUARANTEE:** the census is **per principal kind, by INPUT**, re-run for the agent's id
field — the same discipline that found `policyHealthBadge` had seven sites with four wrong, **two of which
never called the function at all**. ⛔ **The replacement is a repeated measurement, not an inherited claim.**

> ## **A CENSUS IS A STATEMENT ABOUT A MOMENT AND IT IS NOT SELF-RENEWING.** Code added after it is not
> ## covered by it. The unacceptable outcome is not option B — it is a second site added *quietly*, inheriting
> ## a guarantee it was never inside.

### THE CHAIN, IN ONE LINE

**D25 → owner source → table → constructor.** D25 decides whether ownership is an availability dependency;
that decides how durable the source must be; the table decides what is inherited free; the constructor is the
only one that can be re-argued after the fact — **and it is the only one whose guarantee lapses silently if
nobody re-argues it.**
