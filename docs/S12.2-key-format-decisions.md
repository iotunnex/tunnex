# S12.2 — the licence key format and offline verification. Commit-one.

**Status: ⛔ PAPER. Decide-items in §7 are HELD. No product code.**

Taken before S12.1 on the founder's ruling: **it makes the work already built live.** A key minted by the
issuance service today verifies **nowhere** — `grep -rl "tnxl_" apps/api apps/node` is empty. This story
closes the loop **request → sign → email → paste → verify** before 1,784 lines get relicensed for S12.1.

---

# 1. SCOPE, AND IT IS DELIBERATELY NARROW

**IN:** the wire format · Ed25519 verification against a baked-in public key **SET** selected by `kid` ·
fully offline · **reading the claims out**.

⛔ **OUT, and this is the line that matters: NOTHING IS GATED.** No capability is switched on or off by a
claim. `LicenseManager.Claims()` returns what the key says and the caller ignores it. **Gating is S12.1**,
and mixing the two would mean a bug in verification becomes a customer locked out of a feature, in the same
slice that first parses an unfamiliar format.

⛔ **Also out:** build tags · the entitlements map · anything in `tunnex-web` except the golden vector.

## 1.1 ⛔ FULLY OFFLINE IS THE PRODUCT'S PROMISE, NOT A FEATURE OF THIS STORY

**No network call, ever. It must work air-gapped.** That is the reason a sovereignty buyer chooses Tunnex,
and it is what makes revocation impossible (`docs/laws.md` — *a product promise that is the absence of a
channel*). **A verifier that "falls back to an online check" has broken the product, not improved it.**

The check must therefore be provable by construction: **the verifier package imports no network package at
all**, and a census asserts it — §5.

---

# 2. ⛔ THE FORMAT — AND IT DOES NOT MATCH WHAT WAS SCOPED

**The signer already exists** (`tunnex-web/src/lib/licence.ts`) and emits this, measured:

```
tnxl_<base64url(payload JSON)>.<base64url(ed25519 signature over the payload segment)>

payload = { v, kid, id, dom, band, gw, iat, exp }
```

The scope for this story named: **tier · gateway_band · expires_at · licence_id · company · kid**.

| scoped | signer emits | status |
| --- | --- | --- |
| `kid` | `kid` | ✅ |
| `licence_id` | `id` | ✅ (name only) |
| `expires_at` | `exp` | ✅ (name only) |
| `gateway_band` | `band` + `gw` | ⚠ the band **and** its resolved ceiling |
| **`tier`** | — | ⛔ **ABSENT** |
| **`company`** | `dom` (a **domain**) | ⛔ **NOT THE SAME FIELD** |

> ## ⛔ **THIS IS THE LAST MOMENT THE FORMAT IS FREE.** Nothing has been issued, the signer's branch is
> ## unmerged, and no customer holds a key. **After the first real issuance, a format change is a change to
> ## artefacts that cannot be recalled** — every key in the world would have to be re-issued, and offline
> ## verification means we cannot even find out who holds one.

The two gaps are **D1** and **D2** in §7. They are held, not guessed.

## 2.1 What is settled about the format

- **`v`** — a wire version. A verifier that meets `v` it does not know **refuses**; it must never
  best-effort a payload whose shape it is guessing at.
- **`gw` is resolved AT MINT**, not looked up at verify. A later change to the band table must never
  silently re-price a key already in a customer's hands (a grant nobody re-issued).
- **`null` for unlimited**, not a sentinel — a sentinel is a ceiling somebody eventually hits.
- **The signature covers the payload segment as transmitted**, so verification never re-serialises JSON.
  ⚠ **That is load-bearing**: Go and JavaScript do not agree on key order or number formatting, and a
  verifier that re-encoded before checking would fail on keys that are perfectly valid.

# 3. ⭐ THE CROSS-REPO PROBLEM IS THIS STORY'S REAL WORK

The signer is TypeScript in `tunnex-web`. The verifier is Go here. **They must agree byte-for-byte and
cannot import each other.**

This repo has already solved exactly this, twice, and the mechanism is named in `docs/laws.md`:

> **An INDEPENDENT restatement is the mechanism** — the twin canonical-hash goldens, the mirror census as a
> deliberate literal, the D10 golden vector. **A check must be able to DISAGREE with the thing it checks.
> Derivation removes that ability while looking like rigour.**

## The design: ONE golden vector, TWO hand-maintained assertions

A frozen triple — **a fixed key pair, fixed claims, and the exact wire string** — asserted in **both**
repos:

| repo | what it asserts |
| --- | --- |
| `tunnex-web` | signing those claims with that key **produces that exact wire string** |
| `tunnex` (here) | verifying that exact wire string with that public key **yields those exact claims** |

⛔ **HAND-MAINTAINED IN EACH. NEVER GENERATED, NEVER SHARED VIA A PACKAGE, NEVER FETCHED.** The moment one
side derives the vector from the other, the two files stop being independent and **agree by construction** —
which is the failure the twin goldens exist to prevent, and it would pass for every possible format
including a broken one.

⚠ **A format change must break BOTH, or the guard is decorative.** That is the property: the pain of
updating two files by hand *is the mechanism*. Anyone who finds that duplication annoying and factors it out
has removed the only thing it was doing.

**The vector includes a deliberately awkward case** — a `null` gateway ceiling, a unicode company/domain
value, and a large `exp` — because the failures that survive are encoding disagreements, not happy-path
ones.

# 4. THE PUBLIC KEY SET IN THE BINARY, AND WHAT ROTATION COSTS

**The set is a Go literal, compiled in.** Not a file, not an env var, not config.

> ## ⛔ **BAKED AT BUILD TIME MEANS A ROTATION IS A RELEASE. Say it that way — calling it "configuration"
> ## implies an operator could fix a compromise, and they cannot.**

Rotation, end to end: generate a key with a new `kid` → **add its public half to the literal** → ship a
release → customers upgrade → issue under the new kid → **later, delete the old kid from the literal** →
ship another release.

⭐ **D4 (already ruled) is what makes that expressible**: keys carry a `kid` and the verifier selects from a
set. ⛔ **It does not make rotation cheap** — keys minted under the old kid run to their own expiry, the
installed base still has to upgrade twice, and compromise remains undetectable. It removes the *format*
migration that would otherwise sit on top of the upgrade migration.

⛔ **AN UNKNOWN `kid` IS A REFUSAL, NEVER A FALLBACK to "the only key we have."** A fallback turns the set
back into a single key and accepts keys signed by a retired — possibly compromised — kid, while every other
test stays green. The signer's test suite already names this; the verifier will carry the twin.

# 5. WHAT A BAD KEY DOES — REFUSE LEGIBLY, GATE NOTHING

Every outcome is **a typed reason the operator can act on**. ⚠ **And in this story every one of them is
INERT**: the deployment behaves identically. The claims are read and reported; nothing is switched off.

| outcome | what it means | what the operator sees |
| --- | --- | --- |
| `ok` | signature valid, `kid` known, not expired | the claims, and the expiry date |
| `malformed` | not `tnxl_`, bad base64, unparseable JSON | *"this does not look like a Tunnex licence key"* |
| `unknown_version` | `v` is newer than this build understands | ⭐ *"this key needs a newer Tunnex"* — **the one refusal whose remedy is an upgrade, and it must say so** |
| `unknown_kid` | signed by a key this build does not trust | *"this key was not issued by this Tunnex"* — a retired or foreign signer |
| `bad_signature` | tampered, or truncated in transit | *"this key is not valid"* |
| `expired` | `exp` is in the past | the expiry **date**, not "expired" alone — the date is what makes it actionable |

⚠ **`expired` is reported, not enforced.** Grace, warnings and what stops working are S12.1's degradation
rules. A key that is 400 days old parses, verifies, and reads as expired — **and the deployment does
exactly what it did before.**

# 6. ⛔ THE CLOCK — HIGH-WATER MARK, WHICH REPORTS AND NEVER REFUSES

`exp` is checked against **the deployment's own clock, which can lie in both directions**, and offline
verification means there is no second opinion.

- **Forward lie** (clock ahead) → a live key reads as expired.
- **Backward lie** (clock behind, or reset) → an expired key reads as live. ⚠ **This is the direction an
  attacker would choose**, and it is trivially available on a self-hosted box.

**The ruled mechanism: a persisted high-water mark.** Record the highest wall-clock time ever observed; if
the clock is now materially *behind* it, that is a backward jump.

> ## ⛔ **IT DETECTS AND REPORTS. IT NEVER REFUSES.**

**Why refusing would be wrong**, and the reason is the same one that runs through the whole model: a clock
that goes backwards is **overwhelmingly** a VM restore, an NTP correction, a hardware fault, or a container
image with a stale clock — **not an attack**. Refusing on it would take a working VPN down over a plausible
accident, violating *a running VPN never stops*. And an attacker who controls the box can also delete the
high-water file.

⭐ **So it is honest instrumentation, not a control**: it makes the anomaly visible to an operator who is
looking, and claims nothing more. ⚠ **Recorded as a SUBSTITUTE, not a defence** — the real answer to clock
lying is short-lived keys with reissue, which is the revocability question already on the record.

# 7. DECIDE-ITEMS — HELD

## ⛔ D1 — `tier` IS ABSENT FROM THE FORMAT. SHOULD IT EXIST?

Under the S12.1 model, **tier is Community or Enterprise** — and **Community has no key at all.** So
*holding a valid key* IS being Enterprise, and a `tier` field would be a constant that only ever says
`enterprise`. Bands (`trial`/`starter`/`growth`/`scale`) already carry the commercial distinction.

**Recommendation: no `tier` field.** A field with one possible value is a field that will be misread as
meaningful, and the first person to add `tier: "community"` will have invented a key for a tier that is
defined by not needing one. ⚠ Held because the scope named it.

## ⛔ D2 — `company` vs `dom`: WHAT IS THE KEY BOUND TO?

The signer emits **`dom`, a domain** (`acme.com`), derived from the verified work email via eTLD+1.

- **A domain is a BINDING** — machine-comparable, already proven by the trial's email verification.
- **A company name is a LABEL** — for display, unverified, and a customer will want theirs spelled right.

**Recommendation: keep `dom` as the binding, and add `co` as an OPTIONAL display label.** ⚠ And say plainly
in the verifier that **`co` is decorative** — a name nobody verified, shown but never compared. Otherwise a
future reader will gate on it.

## D3 — the high-water mark's storage location and granularity (a file? a DB row? per-process?)

## D4 — does the golden vector live in a `testdata` file or as a Go/TS literal?

**Recommendation: a literal in each repo's test.** A shared file format is the first step toward a shared
file, and the whole property is that nothing is shared.

# 8. WHAT THIS STORY DOES NOT DO

- **Gate anything.** No capability changes behaviour. That is S12.1.
- **Touch build tags or the entitlements map.** S12.1.
- **Change `tunnex-web`,** except to add the golden vector to its test suite.
- **Answer revocation.** Still impossible, still by design.

⛔ **And it does not merge the issuance branch.** That is a separate act; this story only makes the key it
mints mean something.
