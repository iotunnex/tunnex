# S12.5 — the org question. Commit-one, decisions only.

⛔ **A CUSTOMER CAN PAY FOR SOMETHING THEY CANNOT USE.** `multi_org` became a paid Enterprise capability in
S12.1. The pricing page sells it, the licence unlocks it, the API serves it — **and the web UI throws away
every organization but the first.**

This is not a gap discovered by inspection. It is a **contradiction the licensing work created**: before
S12.1 the second org was unreachable *and unsellable*, which was consistent. Selling it made the
discarding a defect.

---

### 1b. ⛔ THE THREE SURFACES GIVE THREE DIFFERENT ANSWERS — measured, not assumed

| Surface | What it does with a user's N organizations |
|---|---|
| **API** | Serves **all of them**. `GET /api/v1/organizations` returns every membership; `authctx.Principal.Roles` is `map[uuid.UUID]string` — orgID → role. **The server has been multi-org the whole time.** |
| **Electron client** | Uses **all of them**. `httpdeviceapi.ts:126 orgIds()` returns `orgs.map(o => o.id)` and the caller iterates. ⭐ **The desktop app is already correct** — it was never the client that discarded. |
| **Web UI** | Uses **the first**, fourteen times over. |

⚠ **This corrects the framing this story was handed.** It is not "the client discards what it was handed" —
**one of two clients** discards. Electron and the API agree; the web app is the sole dissenter, and any
design that adds a server concept of "current org" would have to break Electron to do it.

### 1c. ⚠ THE LOGIN PAGE'S `Organization` FIELD DOES NOT SELECT A TENANT — CONFIRMED, STILL TRUE

`pages/Login.tsx:301`. Its value flows to exactly one place:

```ts
api.GET("/api/v1/auth/sso/{provider}/start", { params: { path: { provider }, query: { org } } })
```

**Nowhere else.** It is a required query parameter of the SSO start endpoint — the IdP cannot be chosen
without knowing the tenant — and it is **not read on the password path at all**. A user who types an org
slug and signs in with a password is not sent to that org.

⛔ **AND THAT IS A SEPARATE DEFECT, NOT A DETAIL OF THIS ONE:** the field is visible to every visitor,
labelled `Organization`, with placeholder `acme`. It looks exactly like tenant selection. **A user in two
orgs will type the one they want and land in the other**, and nothing will tell them why.

## 2. THE THREE SHAPES — with costs. ⛔ HELD. None is ruled.

### A — Pick-on-login
A chooser after authentication when N > 1; the selection is stored and used for the session.

**Cost:** every entry into the app costs a decision, including the ~100% of users with one org — unless
gated on `N > 1`, which makes the flow conditional and the tests two-pathed. ⚠ **And it answers the wrong
question**: an admin comparing two tenants must sign out to switch.

### B — A switcher in the shell ⭐ RECOMMENDED, AND THE REASON IS THAT NOTHING SERVER-SIDE CHANGES

One `useCurrentOrg` context at the shell, defaulting to the first org, persisted; a switcher in the header
when `N > 1`; **the fourteen call sites read the context instead of index zero.**

**Cost:** fourteen call sites edited, and each one's loading/error path re-verified — they currently
*fetch* the list, so they lose a fetch as well as gaining a source. Every page must handle the org changing
underneath it (refetch on switch, not on mount alone).

⭐ **Why it is the recommendation:** the API is already multi-org, Electron is already multi-org, and
`RequireOrg` is already org-agnostic. **B is the only shape where the fix is entirely inside the surface
that is wrong.** A and C both add a concept the server does not have, and both would require Electron —
which is correct today — to be changed to stay correct.

⚠ **It also discharges a deferred item by name**: the `useCurrentOrg` hook, deferred since S4 and cited in
`App.tsx`'s own comment.

### C — Server-side "current organization"
A session-scoped current org, set by an endpoint, honoured by unscoped routes.

**Cost:** the highest, and it buys a property nobody asked for. Every `{orgId}` route already takes the org
explicitly — that is the RBAC boundary. ⛔ **Introducing an implicit session org creates a second way to
address a tenant, and two addressing modes is how a request ends up authorized against one org and executed
against another.** Also breaks Electron, which passes org IDs explicitly and correctly.

## 3. ⛔ WHATEVER THE SHAPE — the three surfaces must be made to agree

The measurement's real finding is not `orgs[0]`. It is that **API, login page and web UI answer the same
question three ways**, and no test anywhere asserts they agree.

**In scope regardless of which shape is ruled:**

1. The login `Organization` field is **labelled as tenant selection and is not**. Either it selects the
   tenant on every path, or it is labelled for what it is (SSO tenant hint) and hidden on the password path.
2. **A guard that fails when a new call site reads index zero.** Fourteen sites drifted to the same defect
   independently because nothing named it. ⚠ Subject must be **the capability** — "which org does this page
   act on" — not the string `[0]` (`docs/laws.md`).

## 4. ⚠ WHAT THIS STORY DOES NOT DO

**No user counting, no seat gates** (founder standing rule). A switcher shows organizations the user is
already a member of; it grants nothing and counts nobody.

**No change to the org ceiling.** Creating orgs stays licence-gated at creation (S12.1 §3). This story is
about reaching orgs that already exist.
