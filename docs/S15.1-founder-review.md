## What this story actually changed

A machine credential could not name a person. `machine_credentials` had **no `user_id` column**, so
every machine principal that has ever authenticated against this control plane did so **ownerless** —
the audit trail recorded *a machine*, never *whose machine*. S15.1 adds the column, the principal
field, the refusal, and the surface that assigns it.

> ⛔ **THE REFUSAL IS THE STORY, NOT THE PICKER.** An unassigned credential no longer authenticates —
> `MachineAuth` returns `nil, nil` when `user_id` is NULL. The picker exists so that refusal is
> *recoverable* rather than a wall.

## 1. The four per-row states — org `demo`

Five rows. Read the right-hand column of each; the four combinations are all present deliberately.

| row | owner | last seen |
| --- | --- | --- |
| `gitops-prod` | — unassigned | never seen |
| `gitops-staging` | — unassigned | ~2 hours ago |
| `ci-runner` | owner@demo | ~11 minutes ago |
| `backup-agent` | owner@demo | never seen |
| `k8s-operator-us-east` | — unassigned | never seen |

**What to look at:** `never seen` must read as a *fact*, not as an error or a blank. It is the honest
rendering of `last_used_at IS NULL` — a credential minted and never used.

⚠ **The two unassigned-with-an-owner rows are the ones that matter.** They are what the assignment
flow produces, and they are seeded rather than clicked so you are reviewing the *rendering*, not your
own click.

## 2. The banner — switch to org `demo-migrated`

Two rows, both owned. The banner appears: **every machine credential has an owner**.

> ⛔ **IT NEEDED A SECOND ORG, AND THAT IS NOT ARBITRARY.** The banner is
> `creds.data.every(c => c.owner_user_id)` — one unassigned row anywhere in the org suppresses it. So
> a second *set* inside `demo` could not reach the state; only a second *org* can.

⚠ **And assigning the two demo rows to reach it would have reviewed a different thing.** That
exercises the assignment flow and leaves the banner glimpsed at the end of an interaction, rather
than seen as the screen's own answer to *is the migration done*.

One row here has a last-seen and one has never been seen — so if the banner is accidentally coupled
to that field, it shows here rather than in production.

## 3. The assignment flow — back in `demo`

Assign an owner to `gitops-prod`. The picker opens with **"Choose an owner…"** selected, not with a
person pre-selected.

⛔ **Deliberate.** A pre-selected first-in-list owner means a mis-click writes a *plausible* wrong
owner into an audit-bearing field, and nothing downstream can tell it from a decision.

After assigning, the row moves to owned. The banner does **not** appear — four rows are still
unassigned, which is correct.

⛔ **§3 IS ONE-WAY, AND RE-SEEDING DOES NOT UNDO IT.** There is no unassign: the API exposes
`assignMachineCredentialOwner` and `revokeMachineCredential`, and nothing that clears an owner back to
NULL. Re-running `make seed-fixtures` will *not* restore the row either — the insert is
`ON CONFLICT (id) DO NOTHING`, so an already-present row is left exactly as you left it.

To put §1 back, org-scoped:

```sql
UPDATE machine_credentials SET user_id = NULL
WHERE org_id = '01900000-0000-7000-8000-000000000001' AND name = 'gitops-prod';
```

⚠ **Whether "no unassign" is right is a live question, not a settled one.** D19 ruled
assign-explicitly; it did not rule on reversal. A wrong owner is currently only correctable by
revoking the credential and minting a new one — worth your ruling, and out of scope for this slice.

## 4. The three empty states

Not reachable from the demo data by clicking; named here so you know they exist and what they say.

| state | when | why it is not a blank |
| --- | --- | --- |
| `load-failed` | the list request fails | says the list could not be loaded — it does not render as "no credentials", which would be a **false zero** |
| `none` | org has zero credentials | says there are none, and offers the create path |
| `all-owned` | every row owned | the §2 banner |

⚠ **`load-failed` versus `none` is the point.** A failed load rendering as an empty list is a zero
nobody measured — this repo's recurring defect class, and the reason the three are distinct
`data-state` values rather than one falsy branch.
