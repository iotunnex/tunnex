## 2.2 ⛔ ABSENT-PENDING-ENDPOINTS — the `TUNNEL` class

| element | measured absence |
|---|---|
| **AUTH column** (`Google SSO` / `Entra SSO` / `Local + pwd`) | no auth-source field on `Member` |
| **MFA column** (`TOTP ✓` / `Enroll req.`) and **`MFA enrolled 5/7`** | `mfa_enrollment_required` and `recovery_codes_remaining` are on **`AuthUser`**, never `Member` |

**⛔ THE MFA ONE HAS A SHARP EDGE: `adminResetMfa` EXISTS.** So the screen can offer *"reset MFA"* while being
unable to show whether MFA is enrolled — **an action with no visible precondition.** Shipping the button without
the column asks an admin to reset something they cannot see the state of. **Ruled: the action ships only if its
state does; otherwise both wait.**

## 2.3 ⛔ THE INVITATION WORKFLOW GAP — NOT a missing column (founder-reclassified)

Four operations exist and **none of them reads**:

```
acceptInvitation · createInvitation · resendInvitation · revokeInvitation      ← measured at the handlers
```

`resendInvitation` and `revokeInvitation` both take **`EmailRequest`** — an email the admin **cannot look up**.

> ## **AN ADMIN SENDS AN INVITE AND THEN HAS NO SURFACE ON WHICH THAT INVITE EXISTS.**
> ## **THE CAPABILITY SHIPS IN THE API AND IS UNREACHABLE FROM THE UI AFTER THE FIRST STEP.**

This is the **S11 class** — `gateway revoke` existed in the API and never in the UI — **with an extra turn:** here
the first step *is* reachable, which makes the dead end worse, because the admin has already acted.

**⛔ STRONGEST CANDIDATE FOR THE BACKEND STORY** if one gets cut for this epic: `listInvitations` is one read
endpoint that turns three orphaned writes into a workflow. Registered as a workflow gap, not a column cut.

## 2.4 ⛔ `{{ teamMap }}` — and I UNDER-READ IT FIRST TIME

My first pass called it a role-hierarchy graph. **Measured in `buildTeamMap()` / `teamData()`: it is
TRIPARTITE** — `{ roles, users, groups, edges }`, laid out in three columns (`role` x=82, `user` x=300,
**`group` x=518**).

**So group membership IS in the design — as PANEL EDGES, not a roster column.** (Confirmed separately: the
roster has **no `GROUPS` column**; `grep 'group'` over the screen body returns **0**. Recording that
explicitly, since its absence was the open question.)

**Which relocates the N+1 rather than removing it, and adds a permission finding:**

- `listGroupMembers` is **`PermPolicyView`** — measured at `policy_handlers.go:129`, **not `org:view`**
- there is **no per-user reverse lookup**; enumeration is per-group only

> ### **THE NODES ARE SERVED. THE EDGES REQUIRE A PERMISSION THIS SCREEN'S OWN AUDIENCE MAY NOT HOLD.**

A member viewing the roster cannot be shown the edges at all. **CUT — and the reason is a permission boundary,
not a missing field**, which is a different cut than the other four and must not be filed with them.

## 2.5 Copy — ships as copy

**`demoting the last owner is refused server-side`.** ⛔ **MIRRORED FROM THE 403, NEVER PRE-EMPTED
CLIENT-SIDE** — the S4.7 reactive-403 precedent. A client-side owner count would be a second authority on a
rule the server owns, and it would be wrong the moment two admins act at once.

## 2.6 ⛔ AN ADDITION OVER THE WIREFRAME — recorded with the same discipline as a cut

**`email_verified: false` is SERVED, REAL, and ABSENT FROM THE DESIGN.**

An unverified member is a member who cannot act — a real state with a real remedy (resend verification), and
the roster is where an admin would look for it. **Added deliberately, not as an unremarked extra.**

> **ADDITIONS GET THE SAME DISCIPLINE AS CUTS.** A silent addition is as hard to audit later as a silent
> removal, and "the design didn't show it" is the argument that would delete it in six months.

# 4. FIXTURE — a PRECONDITION OF THE BUILD, NOT OF THE REVIEW

Two S14.10 reviews failed on states that were not reachable; **each cost a full cycle.** So before any code:

| state | why it must exist |
|---|---|
| a **deactivated** member | S2.6's distinct render is unobservable without one |
| an **unverified** member (`email_verified: false`) | §2.6's addition has no subject otherwise |
| **all three roles** (owner / admin / member) | `role` is the column the screen is named for |
| a **sole-owner org** | the last-owner 403 cannot be observed any other way |

**Rules, from S14.10:** seed the INPUTS a controller consumes, never a field it owns · any value relative to
`now()` is `ON CONFLICT … DO UPDATE`, never `DO NOTHING` · destructive writes are **org-scoped** · and the
census is read **from the API payload, never psql** (they disagreed in S14.10 and psql was wrong).
