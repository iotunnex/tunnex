## ⛔ A1 — THE FAILOVER CONTROLLER COULD NEVER CLEAR A DEMOTION (permanent wedge) · FIXED

**Severity: high. It stops working exactly when the fleet is already degraded.**

`apps/api/internal/nodes/failover.go`

```go
var demoted []uuid.UUID          // nil
...
if len(configured) >= 2 {        // the ONLY assignment
    demoted = fc.Step(configured, freshness)
}
...
demotedChanged := !sameOrder(demoted, current.Demoted)
```

`org_hub_set.demoted` is **NOT NULL**. A nil slice reaches pgx as **SQL NULL**.

**THE FAILURE:** an org that has a demoted member and then drops below two configured hubs computes
`demoted = nil`, sees `demotedChanged = true` (nil ≠ `{member}`), writes NULL, and gets
`SQLSTATE 23502`. **The tick fails. And it fails again on every subsequent tick, forever** — the controller
is wedged until a human edits the row by hand.

> ## **THE HA FAILOVER CONTROLLER STOPS WORKING AT THE MOMENT IT IS MOST NEEDED,**
> ## **AND SAYS SO ONLY IN A LOG NOBODY IS TAILING.**

**HOW IT SURFACED:** 42 consecutive `failover_org_failed` lines in the CP log. I only looked because an
unrelated 500 sent me to `docker logs`. **Nothing else reports it** — the API is healthy, every screen
renders, the HA panel shows a hub set. A wedged controller is invisible from the product.

**FIX:** `demoted := []uuid.UUID{}`. One word.

**PROVEN ON THE WIRE, not asserted** — after the fix, monitored for 60s:

```
t+10s  failures60s=0  ticks60s=1  demoted={01900000-...-0000000f0003}
WEDGE CLEARED - controller ticking, zero failures
```

**AND `demoted` IS NOW DERIVED** — the controller demoted `ap-south` itself, for staleness.

### A1b — MY FIXTURE CREATED THE TRIGGER, AND WAS WRONG ON ITS OWN TERMS

I hand-wrote `demoted` into `org_hub_set`. **The query comments assign that field explicitly:**

```
ReconcileHubSet's writer: writes `configured` ONLY ... This writer NEVER touches `demoted`
   (the field partition — the controller owns it)
UpsertOrgHubSetDemoted: the failover controller's writer: writes `demoted` ONLY
```

**A hand-seeded demotion is not a stable state** — the controller recomputes it every tick, so the fixture
was describing a world the product corrects. Now the fixture gives `eu-west` and `ap-south` the endpoints the
elector requires (the capability gate is `endpoint` + `wg_public_key`, and both had keys but **no endpoint**,
so the elected set never reached two members and the demotion branch never ran at all) and lets the
controller demote `ap-south` for being stale. **Derived, not declared** — the rule the fixture file already
states for every health kind.

## ⛔ A2 — A SPEC-DOCUMENTED INPUT RETURNS 500 · NOT FIXED, WORKED AROUND

**`POST /k8s/clusters/{id}/services` with `port_low` and no `port_high` returns `internal_error`.**

The spec says it is valid:

```yaml
port_high: { nullable: true, description: "High port; omit for a single port or all." }
```

The database forbids exactly that:

```sql
CHECK ((port_low IS NULL AND port_high IS NULL)
    OR (port_low IS NOT NULL AND port_high IS NOT NULL AND port_low <= port_high))
```

**Nothing validates between them**, so a documented input reaches Postgres and the user gets a 500 with
`"an unexpected error occurred"`. **Three-way disagreement: spec says yes, DB says no, handler says nothing.**

**I DID NOT FIX IT.** It is a mid-build fork (spec change vs constraint change vs handler validation) and the
protocol says those halt and surface. **I worked around it** by sending `port_low == port_high`, which
unblocked the exposure without hiding the defect. **Needs a disposition — see D6.**

## ⛔ C2 — TWO THINGS THE DESIGN SHOWS THAT WE DO NOT SERVE

**`STATE` IS NOT A FIELD.** `K8sService` carries `id, cluster_id, name, namespace, protocol, port_low,
port_high, vip, fqdn, managed_by_operator`. **No state. No readiness.**

- **`VANISHED`** — derivable for a *rule* (`dst_k8s_service_vanished`), but that flag lives on `PolicyRule`.
  An unexposed Service is simply **absent** from the list.
- **`NO READY POD`** — per-Service readiness from an EndpointSlice watch. **Nothing serves it.** The nearest
  thing, `k8s_endpoints_unavailable`, is **node-level** (the gateway cannot see endpoints *at all*), not a
  per-Service verdict.

**Same class as the gateway `PEERS` count and the routed-range device count: a designed column with no field
behind it.** → **D5**

**AND THE HANDOFF'S VIP RANGES ARE `100.64.x` (CGNAT), NOT RFC1918.** `100.64.0.0/10` is a defensible
convention — it cannot collide with a customer LAN. But **the S14.7 address-space map draws only the three
RFC1918 blocks**, so a `100.64` VIP range lands in its **off-map list** rather than on a grid. Honest, but a
cross-screen consequence. → **D8**
