## Slice 1 — VIP-stability disposition (RULED, condition from the F2/D3-condition-3 blessing)

The reassignment hazard is born in ExposeService's allocation. **RULED: identity-resolution alone is
sufficient — allocation does NOT quarantine freed VIPs, and this is safe by construction.** The used-set
(`ListUsedVIPsInCluster`) is LIVE Services only, so a soft-deleted Service's VIP is immediately reusable.
That is safe because a grant references a Service's STABLE ID and the compiler resolves ID → CURRENT VIP
at compile time and **NEVER caches a VIP** (Slice 2): a deleted Service vanishes from the resolution set
(its grant compiles to nothing), and a reused VIP belongs unambiguously to the NEW Service's identity. No
quarantine timer is needed (the rejected alternative — complexity for no gain once grants track identity).
The **reassignment-trap red belongs in Slice 2** (where the resolution is built): prove a deleted Service's
grant compiles to nothing AND a re-exposed Service reusing the freed VIP resolves to the NEW identity only.

## Slice 3b + Slice 4 — ClusterIP resolution RULED (A): in-cluster CoreDNS, no K8s API

The gateway resolves <service>.<namespace> -> ClusterIP via in-cluster CoreDNS and programs a prerouting
DNAT VIP -> ClusterIP. The privilege argument decides it: F4 already takes hostNetwork + NET_ADMIN;
"the gateway needs kernel networking but reads NOTHING from your Kubernetes API" is a materially better
sentence for a customer's security team, and true only under (A). ClusterIP stability makes (B)'s
authoritativeness worth little.

**Ordering (SOUND, not fragile).** Client->VIP hits the gateway's prerouting nat in the NODE netns (F4
hostNetwork is what puts our rules there). Double-DNAT in sequence: our chain VIP->ClusterIP, then
kube-proxy's KUBE-SERVICES ClusterIP->pod -- so OURS MUST RUN FIRST, at a priority NUMERICALLY BELOW
dstnat (-101). Deterministic in nftables; holds across kube-proxy iptables-nft/nft/IPVS modes; conntrack
reverses both DNATs on return. Our DNAT lives in our OWN table ip tunnex (atomic add;flush;table wholesale
replace), never interleaved into kube-proxy's chains -- kube-proxy's resync never touches it, and there is
no foreign-chain drift matching (no S8.6b comparator risk).

**Four conditions (ruled):**
1. **hostNetwork DNS trap (the silent-install-killer).** A hostNetwork pod inherits the NODE's resolv.conf,
   NOT the cluster's -- *.svc.cluster.local won't resolve without `dnsPolicy: ClusterFirstWithHostNet`. The
   gateway chart MUST set it (commented). PREFLIGHT red: cluster DNS unresolvable at startup -> refuse
   loudly (k8s_cluster_dns_unreachable), never program nothing silently.
2. **No stale DNAT.** NXDOMAIN (Service deleted) or a changed ClusterIP -> the rule is removed / updated,
   never kept. A DNAT to a dead ClusterIP is dead-while-green (VIP answers, traffic blackholes). Reds:
   NXDOMAIN -> rule swept + surfaced; ClusterIP changed -> re-programmed within one tick.
3. **Headless Services refused, not guessed.** clusterIP:None returns pod IPs; DNAT-ing to a pod IP is wrong
   + unstable. Detect at reconcile (the agent sees it via resolution) -> refuse with a typed teaching error
   (headless Services aren't exposable through a VIP).
4. **Bounded staleness (paper):** ClusterIP changes propagate within ONE reconcile tick -- the fourth
   honest-bound sentence in the ledger (OVPN reneg, OVPN re-home, K8s version gate, now this).

**(B) is satisfied-by-the-operator, not deferred-as-a-gateway-change.** When S10.2's operator exists it
inherently has K8s API access (it watches CRDs), so it can supply authoritative ClusterIPs to the CP --
improving accuracy WITHOUT the gateway ever gaining API permission. Register (B) satisfied-by-operator;
trigger = a customer needing sub-tick ClusterIP propagation. The privilege boundary stays where it belongs.

## Slice 4 — agent DNAT (SPEC for the fresh session; highest-privilege, undiscounted review after)

Build in a fresh session. Prerouting DNAT VIP->ClusterIP at priority < dstnat in table ip tunnex (own
atomic-replaced table), fed by the resolved VIP map; CoreDNS resolver (<service>.<namespace> -> ClusterIP),
injectable. Resolution runs in the RECONCILE (async, network), producing a resolved VIP->ClusterIP map;
rulesetWith renders the prerouting chain PURELY from it (no DNS in the sync render path).

**The four ruled conditions** (see the ruling above): (1) chart dnsPolicy ClusterFirstWithHostNet +
PREFLIGHT k8s_cluster_dns_unreachable; (2) no stale DNAT (NXDOMAIN -> swept+surfaced, ClusterIP change ->
re-programmed within one tick); (3) headless refused; (4) bounded-staleness sentence (written).

**Two additions carried in (checkpoint framing):**
- **Red the atomic-replace-is-free-sweep property EXPLICITLY** (the whole shared-territory argument rests on
  it): a removed Service's DNAT is GONE after one reconcile with NO explicit delete logic, and a simulated
  kube-proxy full-resync in between changes nothing about our table. The S8.6b lesson INVERTED — we avoid the
  comparator entirely, and this red is what makes that structural rather than assumed.
- **Substitute vs walk honesty (WF-OVPN-1 / reaper-red lesson, twice-learned):** the injectable resolver
  means the REAL resolver path is untested by construction. SUBSTITUTE-PROVEN = the injectable path (render,
  sweep, NXDOMAIN/headless handling, priority ordering in the rendered text). OWED TO THE WALK = real CoreDNS
  resolution, real kube-proxy interaction, real priority ordering in a live netns. **The walk leg for this
  slice is the epic's most important: a client reaching a real in-cluster Service through the VIP.**

**FINDING-BEFORE-CODE (surfaced while mapping the resolver) — headless detection is DNS-limited under (A).**
Condition 3 says "detect + refuse headless." But via DNS alone (no K8s API), a normal ClusterIP Service
resolves to 1 IP (the ClusterIP) and a headless Service to N pod IPs — so **multi-pod headless is detectable
(>1 IP -> refuse), but a headless Service with exactly ONE ready pod is INDISTINGUISHABLE from a ClusterIP
at a single resolution** (both are 1 IP). The agent can't know the Service/Pod CIDRs without the K8s API to
classify the address. **Lean (rule at the fresh session's start):** refuse the detectable case (>1 resolved
IP -> headless_service_not_exposable, typed); the 1-pod-headless edge is treated as an (unstable) ClusterIP
and re-resolved each tick (condition-2's re-program-on-change bounds the instability) -- REGISTER it as a
residual, trigger = a customer exposing a 1-pod headless Service. This keeps (A)'s no-K8s-API boundary; the
authoritative fix is (B) satisfied-by-the-operator (the operator reads clusterIP from the API). This is the
one Slice-4 decide-item; everything else is ruled.

**Reds (fresh session):** DNAT present for a resolved Service -> absent after removal (atomic free-sweep,
no delete logic) · kube-proxy resync changes nothing about our table · idempotent across ticks · non-cluster
gateway renders NO prerouting chain · NXDOMAIN -> swept + surfaced · ClusterIP change -> re-programmed · >1-IP
(headless) -> refused + surfaced typed. Then the undiscounted review on the DNAT + privileged surfaces.

## Slice 4b — the three fail-closed terms (ratified; the fresh session opens on execution)

1. **Fail-closed is the default at EVERY branch.** The ONLY path that programs a DNAT is
   exactly-one-address-inside-the-registered-Service-CIDR. Every other outcome -- resolution error, DNS
   server unreachable, NXDOMAIN, >1 address, an address outside the Service CIDR, a missing/bad Service CIDR
   -- programs NOTHING. Structure it so `ok=true` is reachable at literally ONE return (a single classify()
   whose success is the last line), not a series of guards a future edit could reorder into a fail-open.
2. **No DNS in the sync path.** resolve-and-classify runs in the reconcile (async), the render is PURE. A
   slow or hanging resolver must NEVER stall the apply path (the KILL-SWITCH-NO-UNBOUNDED-I/O law's cousin):
   resolution stores the resolved map; rulesetWith reads the last-resolved map and does no I/O. Resolution
   is bounded (per-lookup timeout) and decoupled from the nft apply.
3. **Substitute vs walk, stated in the gate report.** The injectable resolver PROVES the classifier (every
   fail-closed branch + the single success). Real CoreDNS resolution, real kube-proxy chaining, and real
   priority ordering in a live netns are WALK-OWED. The walk leg -- a client reaching a real in-cluster
   Service through its VIP -- is the epic's most important proof.

## Slice 5 — DNS: RULED (A1) direct-answer-from-VIP-map + (B2) Tunnex per-cluster zone

**D3 AMENDED.** D3 ruled "forward to CoreDNS + REWRITE the ClusterIP answer -> VIP." That was written
BEFORE the gateway held an authoritative service->VIP map (Slices 3/4 created it). With the map, the
rewrite is unnecessary machinery around an answer we already have. **(A1) direct-answer:** the gateway
answers a Service name -> its VIP straight from the map; an UNEXPOSED Service (not in the map) -> NXDOMAIN.
The decisive argument is CORRECTNESS, not simplicity: forwarding+rewriting an unexposed Service would
return a ClusterIP that is NOT DNAT'd and NOT routable -- a confidently wrong answer. (A1) makes DNS
SELF-GATING: only exposed Services resolve, NXDOMAIN otherwise, matching the policy surface exactly.

**ONE-TRUTH COUPLING (record it):** the DNS answer and the DNAT program are now derived from the SAME
service->VIP map, so they CANNOT disagree -- one truth, two consumers, the pattern this project has landed
on repeatedly (uapi field omission, ranges-free mint, keyless-peer guard, shouldRenderQR, invalid_vip,
now DNS-answer==DNAT-target).

**(A1) conditions:** unexposed -> NXDOMAIN, NEVER a silent timeout (a client hanging on an unresolvable
name is the worst failure shape). Fail-closed like the classifier: an EMPTY or STALE map answers NOTHING
rather than something.

**(B2) Tunnex per-cluster zone** `<service>.<namespace>.<cluster>.<zone>`. (B1) native svc.cluster.local
REFUSED: it collides across clusters AND forwarding *.svc.cluster.local from a laptop HIJACKS the
well-known cluster-internal zone -- breaking any user who also runs kubectl against a local cluster, in a
way they'd never trace back to us. (B2) is collision-free by construction, self-describing at the point of
use, and rides S8.4's dns_forwarding rail UNMODIFIED (the CP pushes <cluster>.<zone> -> gateway-IP as an
ordinary entry -- reuse the rail, don't fork it).

**(B3) both REFUSED for v1:** accepting the native name buys single-cluster convenience and inherits (B1)'s
hijack the moment a second cluster or a local kubectl appears -- a footgun that arrives later, hardest to
diagnose. REGISTERED, trigger = a design partner explicitly wanting native-name convenience on a known-
single-cluster deployment.

**(B2) conditions:** <zone> operator-configurable (F6-like) with a sane default · the cluster NAME validated
as a DNS label at RegisterCluster (typed teaching error -- it's about to become part of a hostname) · the
zone must pass the existing S8.4 dns_domain_conflict check (one zone -> one resolver org-wide; a second
cluster claiming a colliding zone is REFUSED with the existing typed error, never a silent overwrite) · the
naming shape lands in the docs + the expose/export UI (the string every user types).

## Slice 5 — mid-build FORK: cross-site push collides with SetDNSForward's D7 invariant (RULED (A))

**The claim above is RETRACTED (both kept so the reasoning survives).** The build spec asserted the entry
"rides the S8.4 rail unmodified" and "DNSDomainConflict passes for FREE." That assumed a compatibility the
rail forbids: `sites.SetDNSForward` enforces (S8.4 D7) that the resolver_ip live INSIDE one of the site's
APPROVED subnets ("the resolver lives on the LAN the site fronts"). The K8s DNS VIP is a SYNTHETIC address
deliberately DISJOINT from every site subnet — so SetDNSForward structurally REJECTS it
(`dns_resolver_not_in_site_subnet`). The two designs collide; the "unmodified reuse" was an illusion.
