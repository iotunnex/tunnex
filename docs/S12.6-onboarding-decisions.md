### ⭐ 5 IS ALREADY BUILT — MEASURED, NOT ASSUMED

The scope handed to this paper marked it *not built*. **It works today, end to end, on a live rig:**

```
POST /organizations/{id}/invitations   → 202  {"invite_token": "..."}
POST /auth/invitations/accept          → 200  (invitee supplies name + THEIR OWN password)
POST /auth/login                       → 200
```

`invites.go:158` calls `CreateUser` itself and `/auth/invitations/accept` is `security: []`, so **the invite
mints the account** — being invited IS the admission, and the account is only the credential.
`AcceptInvite.tsx:15` already says *"the invitee sets a password here"*. **An admin never sets someone
else's password**, and never could.

⛔ **So the remaining work on 5 is a WALK, not a build** — the API and the screen exist; nobody has driven
invite → email → link → password → sign-in through the UI with mail delivery. Recorded as a proof owed, not
a feature owed.

### ⭐ 3 — why the bootstrap admin is pre-verified

`admin@tunnex.local` is **a synthetic address the deployment minted for itself.** It has no mailbox, so no
verification mail can arrive, and there is no claim to prove — nobody asserted ownership of it.

⛔ **Guarded by `WHERE email_verified_at IS NULL` on the verify path**, so a pre-verified row can never be
used to verify a REAL address. Pre-verifying an identity is only safe when the identity is not a claim.

### ⭐ 8 — domain capture, and why it needed nothing

It mints its user on the **SSO callback** (`LinkCreate`) and never touched `/auth/signup`, so closing signup
could not break it. And it admits only on a claim that is `verified_at IS NOT NULL` **and** re-proven by a
**live DNS-TXT check at every login**, suspending the claim when that proof disappears.

⚠ **Stronger than "verified once".** Claiming a domain admits nobody.

## The axis — settled

⛔ **Generalise `users.can_create_orgs` into `users.cp_admin`.** `can_create_orgs` becomes IMPLIED by it,
never a second column.

> ⚠ **Two booleans that must agree is the `bandGateways`/`BANDS` shape again** — one set of facts with two
> homes, drifting silently until something built on the stale one ships.

⛔ **NEVER FOLD IT INTO `Principal.Roles`.** The tempting shortcut is to synthesise an `owner` entry for
every org at session-build time.

> ⛔ **That would make `RoleIn` LIE, and every `authorize()` call site would start returning true for
> tenants the user is not in** — a cross-tenant grant leaking into every org-scoped check in the product.

⭐ **The CP-admin check is a separate question asked BESIDE `RoleIn`**, never inside it.

## Invariants — reds required, both directions

| ⛔ | why |
|---|---|
| CP admin cannot remove an org's **last owner** | `CountOwners` exists because this went wrong once; a cross-tenant actor is the one most likely to do it by accident |
| CP admin cannot demote **themselves when last** | a deployment with no CP admin **and no signup** is unrecoverable — today's ruling removed the escape hatch |
| Every cross-tenant grant is **audited** — who, what, which org | it is the only act in the product that crosses a tenant boundary |
| The org's **own owner** sees it in THEIR audit log | ⚠ a privilege change inside your tenant, by someone outside it, is something you are owed sight of |

⚠ **Both directions, or it is a refactor:** the holder can grant, and a non-holder is refused. The second is
the ruling; without it the boundary is just "signed in vs not".
