# S14.2 — LAYOUT SHELL: NAV · RESPONSIVE GRID · BREAKPOINTS

**COMMIT-ONE PROPOSAL. NOTHING BUILT. Awaiting the founder's ruling.**

Imports **no generated types** (EPIC 14 slice-order rationale), so it still cannot conflict with S13.1.

## THE TWO DECIDE-ITEMS ARE ANSWERED — carried in as rulings

**1. MOBILE IS A TRIAGE SUBSET, not the full dashboard.**

| on mobile | surfaces |
|---|---|
| **full function** | gateway/fleet health · the device-approval queue · revoke |
| **READ-ONLY, with an honest line saying so** | everything that COMPOSES a policy — the access-rule builder with source, destination, port scope, expiry |

**Rationale, recorded:** a rule builder on a phone is a security surface where **a mis-tap grants access**, and
a bad one is **worse than none**. **Never a degraded editor** — read-only and honest about it.

**2. DENSITY IS CUT — as CUT-WITH-A-SEAM, not dropped.** Five widths × three themes is enough; at mobile width
*compact* and *cozy* are the same decision made twice. **Build the spacing scale so density COULD return; ship
one density.**

# D1 — THE BREAKPOINT SET, AND WHAT EACH IS *FOR*

**Named by what the user can DO at that width, not by device.** A pixel value is an implementation detail; the
capability is the decision.

| name | from | **what it is FOR** |
|---|---|---|
| **triage** | 0 | **Read state and act on queues.** One column. Approve, revoke, read health. **Composition is read-only here.** |
| **compose** | 768 | **Everything triage can do, plus authoring** — the rule builder becomes available, single-column forms. The first width where a policy may be composed. |
| **operate** | 1024 | **Multi-panel.** The full labelled nav rail; side-by-side detail + list. |
| **wide** | 1440 | **The wireframe's native design width.** Full dashboard grid, the layout the artifact was drawn at. |
| **max** | 1920 | **Clamp, do not stretch.** Content max-width holds; the extra space is margin. |

**The `compose` boundary at 768 is the load-bearing one** — it is where a security capability turns on, so it
is the only breakpoint whose value is a decision rather than a taste. **The others may be tuned freely; this one
is ruled.**

**And it is a FLOOR, not a guess about tablets:** a 768px viewport is the narrowest width at which a
source/destination/port/expiry form can be shown without collapsing fields into an order that invites a mis-tap.

# D2 — NAV BEHAVIOUR AT EACH WIDTH

The wireframe's nav is grouped: **NETWORK · ACCESS · OBSERVE · OPERATE · SETTINGS · OTHER SCREENS**. That
grouping is preserved at every width; only its *presentation* changes.

| width | nav |
|---|---|
| **triage** | Off-canvas drawer behind a menu button, **plus a persistent bottom bar carrying the triage set** (health · approvals · devices). Group headers retained in the drawer. |
| **compose** | Collapsed **icon rail**, labels on focus/hover, groups as separators. Drawer still reachable. |
| **operate**+ | **Full labelled rail** with group headers, exactly as drawn. |

**⛔ THE RULE THAT CONSTRAINS ALL OF IT: responsive may RE-ARRANGE, never REMOVE.** Every nav destination is
present in the DOM at every width. A link hidden by CSS is **invisible, not absent** — still announced to a
screen reader, still keyboard-reachable — and this epic has already ruled that shape a failure (the
theming-vs-edition rule). **Presentation collapses; the link set does not.**

**The one deliberate exception is composition**, and it is the opposite: those controls are **ABSENT** below
`compose`, not hidden. See D3.

# D3 — READ-ONLY ON MOBILE, EXPRESSED **ONCE**

## The shape: **width → CAPABILITY → render decision.** Never width → CSS visibility.

```
useLayoutCapability()  ->  { canCompose: boolean, … }
        │
        └── <ComposeGate>  ── canCompose ──> the editor
                            └─ else ──────> the read-only view + the honest line
```

**ONE component, one hook. Screens declare *what* they compose; they never ask *how wide* the window is.** A
screen that reads a breakpoint directly is the per-screen duplication this decide-item exists to prevent — and
it is the form the drift would take.

## WHY IT MUST BE ABSENCE, NOT `display:none`

**If the rule builder were merely hidden by CSS at triage width, it would still be in the DOM** — focusable,
announced, submittable. **A control that grants access, present to a keyboard and gone only to a sighted mouse
user, is the exact failure the epic's theming-vs-edition rule names: rendered INVISIBLE rather than ABSENT, a
security-adjacent surface failing open.**

**So `ComposeGate` does not render the editor at all below `compose`.** The honest line replaces it:

> *"Access rules are read-only on this screen size. Open Tunnex on a laptop or tablet to edit them."*

**Same seam, same reasoning, three consumers now:** edition (does it exist for this licence), capability (does
it exist at this width), and theme (what does it look like) — **the first two are RENDER decisions, the third
is a style, and they never merge.**

# D3b — THE TOPBAR, AND TWO FINDINGS IN IT

The wireframe's topbar carries: search · Select · Cozy/Compact · FREE/ENTERPRISE · ADMIN/USER · theme dots ·
notifications · help · org switcher · user menu.

**FINDING 1 — THE LIVE NAV COUNTS ARE A DATA DEPENDENCY, not decoration.** The nav renders `Gateways 3/7`,
`Sites 1 DOWN`, `Devices 3`, `Access Policies ENFORCING`. **Those are live values on the SHELL**, which means
the shell — rendered on every screen — acquires a data dependency that no screen owns.

**Consequences to rule at this commit-one:** which endpoint feeds them · what they render **before** it
resolves (**never a stale or defaulted count** — that is the `loadOne` law on the most-seen surface in the
product) · and what they render **when it fails**. **Proposal: absent until loaded, and absent on failure —
never `0`, never a remembered number.** A nav badge reading `0 DOWN` because a fetch failed is the
reassuring-empty defect in the one place every user looks.

**FINDING 2 — FREE/ENTERPRISE and ADMIN/USER ARE READ-ONLY BADGES, NOT TOGGLES** (founder-ruled). They are
wireframe demo controls: **a user cannot switch their own edition or role.** Rendering them as toggles would
offer a control that either does nothing or, worse, looks like a privilege the product does not grant.

**The edition badge READS THROUGH THE ONE GATING SEAM** — the same hook that decides whether enterprise
surfaces exist, never a second source. **The role badge reads the resolved role from the roster**, which is
where `Users.tsx` already gets it.

# D4 — HOW "RESPONSIVE" IS GATED, GIVEN QUERY RULE 4

**Rule 4 says no test may assume a viewport.** That is not an obstacle to gating responsive — it forces the
gate into the only place it is meaningful anyway.

**AND THERE IS A HARD TECHNICAL REASON: jsdom HAS NO LAYOUT ENGINE.** It does not evaluate media queries,
compute widths, or lay anything out. **A "responsive test" that rendered components in vitest and asserted
layout would be asserting nothing** — it would pass at every width because there are no widths. That is a
check that cannot fail, and this repo has a law for it.

## THREE LAYERS, and none of them assumes a viewport

**1. THE BREAKPOINT DECISION IS A PURE FUNCTION — unit-tested, no DOM.**

```ts
layoutIntent(width: number) -> "triage" | "compose" | "operate" | "wide" | "max"
capabilityFor(intent)       -> { canCompose: boolean, navMode: "drawer"|"rail"|"full" }
```

Tested exactly like `policyHealthBadge` and `crossesMultiSiteThreshold` are: **boundary values on both sides of
every threshold**, including `767 → triage` and `768 → compose`, which is the security boundary.

**2. THE COMPONENT TIER IS UNCHANGED AND MUST STAY WIDTH-BLIND.** Its tests assert decisions, never layout, so
they pass at any width **because they never mention one**. **If a component test ever needs a viewport to pass,
that is the finding** — it means a decision leaked into presentation.

**3. THE RESPONSIVE CONTRACT — the assertion that actually protects users.** Render each shell at each
`capability` (injected, not measured) and assert:

- **the nav link set is IDENTICAL across all capabilities** — responsive re-arranges, never removes
- **composition controls are ABSENT at `triage`** — asserted by role, so a `display:none` implementation FAILS
  this test. That is deliberate: **the test distinguishes "hidden" from "absent", which is the whole point**
- **the read-only line is PRESENT whenever the editor is absent** — never a blank space where an editor was

**Mutation proof, as always:** implement the gate as `display:none` and assertion 2 must go red; drop a nav link
at `triage` and assertion 1 must go red.

## WHAT IS *NOT* GATED HERE, AND SHOULD BE SAID

**Actual visual layout at real widths is NOT gated by this slice.** No screenshots, no headless-browser
viewport runs. That is honest scope: it would need Playwright with real viewports, which is `e2e`'s territory
and a different budget.

**PROPOSED: register a visual/responsive e2e leg with a trigger** — the first screen slice (S14.4) — rather
than pretending unit tests cover it. **The capability boundary is gated mechanically; the pixels are gated by
eye until that leg exists.**

# OPEN QUESTIONS FOR THE FOUNDER

1. **Bottom bar at `triage`, or drawer only?** A bottom bar makes the triage set one tap away — which is the
   whole point of the on-call subset — but it is a second nav surface to keep in sync with the drawer. Proposal:
   **bottom bar**, precisely because the triage ruling says those three surfaces are why mobile exists.
2. **Does `wide` (1440) differ from `operate` (1024) in more than column count?** The wireframe is drawn at
   ~1440 with a 1280 floor. Proposal: **same structure, more columns** — no layout that exists only at one
   width, since that is a screen nobody tests.
3. **The honest read-only line — one wording for every gated surface, or per-surface?** Proposal: **one
   wording**, parameterised by surface name, so it cannot drift into fourteen slightly different sentences.
