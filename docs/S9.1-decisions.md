# S9.1 — OpenVPN server management in the node agent — commit-one (decision-first, HELD for ruling)

**EPIC 9 opener.** The wedge epic: OpenVPN is the migration on-ramp for Pritunl/OpenVPN
shops. This is a **port, not greenfield** — the reference spec is the existing Bolster stack
(`openvpn-auth-oauth2` patterns + `genclient`-style PKI), reimplemented inside the node agent.
Nothing built — this paper states the seams, carries the pre-existing ledgered bindings intact,
and holds the S9.1 decide-items for the founder's ruling before any product code.

## Ledgered bindings (PRE-EXISTING — carried unchanged, NOT re-litigated)

These are already ruled (PLAN "EPIC 9", ZTNA coverage batch item 6, S3.3 cross-cutting rule,
S9.3 protocol-selection lock). They frame S9.1; they are not decide-items.

- **B1 — ZT-coverage guarantee (S9.1 DECIDE-BEFORE-CODE, item 6).** OVPN devices are policy
  subjects in the **SAME `policyspec.Compiled` artifact** as WireGuard devices. Grants are
  **transport-agnostic**; cert-auth alone is NOT enforcement. **S9.1 deliberate-red:** an org in
  `enforcing` posture with zero grants → an authenticated OVPN client's traffic is **DROPPED at
  the gateway forward chain, identically to WireGuard**. A parallel, non-compiled OVPN data path
  is a two-door breach — **rejected in advance**. (The compiler already keys a device subject by
  its assigned `/32` + owner + gateway node — `policy.Device{ID, owner, node, address}`,
  `compiler.go:123` — with zero knowledge of transport. An OVPN device is just another `Device`
  row. B1 is therefore a *placement* obligation, not a new compiler concept: see D-S9.1-4.)
- **B2 — identity-binding + full-sweep revocation parity (S3.3 rule, transport-agnostic).**
  Revoking an OVPN device releases *everything it ever claimed*, exactly as WireGuard's
  `devices.Revoke` does today (`devices/service.go:517`): its **pool address** (freed for reuse),
  its **live telemetry/status** (`DeleteDeviceStatus` — no stale "online"), and its **enforcement
  presence** (`PushOrgNodes` strips the compiled grants org-wide). OVPN **adds one member to the
  sweep: a CRL entry** so the running openvpn server rejects the revoked cert on its next connect.
  Cert-revocation ALONE ≠ the sweep; the address/telemetry/grant strip are equally required.
- **B3 — S9.3 protocol-selection LOCKED (not re-opened here).** OpenVPN is consumed via the
  `.ovpn` export (S9.2) by **standard OpenVPN clients** (OpenVPN Connect / Tunnelblick / mobile).
  The **Tunnex desktop client stays WireGuard-only BY CONSTRUCTION** — native OVPN inside the
  privilege helper is the **rejected tier** (the rejected-call-home class, not parked-with-trigger:
  a second data-plane engine in the most expensively-verified component, 2× proof burden forever,
  for a population whose endgame is the WG client we already ship). S9.1 builds the SERVER; it
  builds NOTHING in `apps/client` or the helper.

## The seams (cited)

- **Node agent data plane** (`apps/node/internal/`): today `egress`, `dnsforward`, `reconcile`,
  `nodepolicy`, `control`, `flowlog`. WireGuard is owned via `wgctrl` in a **desired-state reconcile
  loop**. S9.1 adds a **managed openvpn server process** the agent owns the same way it owns wg0 —
  a reconcile target, not a fire-and-forget spawn (D-S9.1-2).
- **Client-cert PKI.** `apps/api/internal/agentca/ca.go` is the **CP↔agent mTLS CA** — 48h leaves,
  **revocation = refuse renewal, NO CRL** (`ca.go:31`, short-TTL IS the revocation). This model
  does **NOT** transfer to OVPN clients: they hold long-lived certs and reconnect at will, so a
  **real CRL is mandatory** (B2). Whether the OVPN client CA is a NEW trust root or reuses the
  agent CA is D-S9.1-1.
- **Device model + revocation** (`apps/api/internal/devices/service.go`): `Revoke` = the 3-part
  sweep above; the device carries a pool `/32` and an owner. An OVPN device is a device row whose
  credential is a client cert instead of a WG public key (D-S9.1-3 addresses address allocation).
- **Policy compiler** (`apps/api/internal/enterprise/policy/compiler.go`): subjects keyed by `/32`,
  transport-agnostic (B1). **Enterprise-tagged** (`//go:build enterprise`) — enforcement is an
  enterprise capability; the OVPN server + PKI scaffolding is edition-independent (D-S9.1-6).
- **Enroll seam** (`apps/api/internal/nodes/service.go:189` `Enroll`, CSR → `SignCSR`): the shape
  a device-cert issue path mirrors — CSR in, signed leaf out, serial recorded for later CRL.

## Decide-items — RULED (founder, 2026-07-24) with conditions

The load-bearing finding frames all six: **B1 is a placement obligation, not a new compiler
concept** — the ZT-coverage guarantee is achievable by NOT forking anything, and every ruling
below protects that.

- **D-S9.1-1 — CONFIRMED (a): a NEW, separate OVPN client CA.** The CRL finding decides it: the
  agent CA is no-CRL / refuse-renewal, built for short-lived agent enrollment; long-lived OVPN
  client certs need real revocation, and reusing agentca would retrofit CRL semantics onto a CA
  deliberately designed without them. Separate CA also gives trust isolation — **an OVPN client
  cert must never authenticate as an agent.** *Condition (paper obligation):* the **CRL is
  data-plane desired state** like everything else — the CP owns it, the agent RECONCILES it, never
  a side channel; and per B2 the cert revocation + CRL push + address release + status clear are
  **ONE sweep, not four independent actions.**
- **D-S9.1-2 — CONFIRMED: agent-owned reconcile target.** A sidecar would create a second lifecycle
  owner for data-plane state — against the day-one desired-state principle. **Sub-question: YES,
  emphatically — the B1 red is SLICE 1.** Prove the enforcement boundary before building the feature
  on top of it (the S8.6 storage-first / crash-sweep-before-resolver ordering discipline). If B1
  can't be proven early, everything after is built on an assumption.
- **D-S9.1-3 — RULED: ONE shared address world; the existing allocator stays authoritative.** This
  is what makes B1 free: an OVPN client's `/32` must be indistinguishable from a WG device's `/32`
  in the compiled artifact — transport-agnostic **by construction, not by a second code path.**
  *Mechanism to state + verify:* OpenVPN self-allocates by default (`server` / `ifconfig-pool`) —
  that must be **DISABLED** in favor of per-client `ifconfig-push` via `client-config-dir` (CCD), so
  Tunnex's allocator remains the single authority. *Conditions:* the allocator's reserved-collision
  logic covers the **OVPN server's own endpoint address**; and the **disjointness validator gains no
  new class** — an OVPN client address is a pool address, full stop.
- **D-S9.1-4 — CONFIRMED (a): co-terminate on the gateway — WITH the condition that decides whether
  B1 is actually free: the forward chain must adjudicate by ADDRESS, not by INTERFACE.** The S8.6b
  arc is the warning (three rounds of orientation predicates — `iifname != wg0`, `wg0→eth0`,
  `wg0→wg0` — because rules keyed on interface geometry rather than the addresses the policy names).
  *Verify BEFORE Slice 1's red:* does the chain's grant emission carry interface predicates that
  would MISS `tun` traffic? If yes, that is the first thing the B1 slice fixes — and D-transit-1's
  "one rule, orientation-agnostic" relaxation is the shape.
- **D-S9.1-5 — CONFIRMED: port PKI/config, re-derive auth from our identity plane.** No parallel
  oauth2 path — that is **B1's sibling risk in its exact form:** an OVPN client authenticating
  through a path the policy engine doesn't see is the two-door breach, rejected in advance alongside
  the parallel non-compiled data path. The Bolster `openvpn-auth-oauth2` stack is a reference for
  MECHANICS, **never an auth authority.**
- **D-S9.1-6 — CONFIRMED: open-edition server + PKI, enterprise inherits enforcement.** Matches the
  S8.5 pattern (one mechanism, edition-gated depth), keeps `test-editions` clean, and matches the
  positioning: **OpenVPN is connectivity, Zero Trust is the enterprise tier.**

## Reds (proposed acceptance set — refined at build after ruling)

- **B1 deliberate-red (the headline):** org `enforcing`, an OVPN device with zero grants → its
  traffic is **DROPPED at the gateway forward chain**; add one allow grant → it flows — byte-for-byte
  the WireGuard behavior. This is the epic's load-bearing proof (wire, on the S9.x walk).
- **compiler transport-agnosticism:** an OVPN `Device` and a WireGuard `Device` with the same `/32`,
  owner, and node compile to the **identical `AllowEntry` set** (the compiler cannot distinguish them).
- **B2 full-sweep parity:** revoking an OVPN device → pool address freed + status cleared + grants
  stripped org-wide + **CRL entry added**; the running server rejects the revoked cert on reconnect.
  A red asserting all four members fire (cert-revoke ALONE is a deliberate FAIL of this red).
- **managed-process reconcile:** killing the openvpn process → the agent restarts it to desired state
  (the wg0 self-heal analog); a config change regenerates + reloads without a full bounce where
  possible.
- **edition:** the open build compiles + serves OVPN + issues `.ovpn`; the enterprise build ADDS the
  policy-subject enforcement — `make test-editions` green both ways (no bleed).

## D-S9.1-4 pre-verification (done before Slice 1, founder-mandated) — B1 IS FREE ON THE VERDICT

The founder's condition: "verify BEFORE Slice 1's red — does the chain's grant emission carry
interface predicates that would MISS `tun` traffic?" **Verified — it does not.** The enforcing
per-grant accept (`apps/node/internal/egress/egress_linux.go:520`, `allowMatch`) renders:

```
ip saddr <src> ip daddr <dst> <proto/port> counter accept
```

keyed **purely by `ip saddr` / `ip daddr` — NO `iifname`, NO `oifname`.** An OVPN client whose
packet arrives on the openvpn `tun` with source = its pool `/32` is adjudicated by the IDENTICAL
rule a WireGuard device hits. **B1 is free on the enforcement verdict — there is no interface
predicate to fix on the grant.** Masquerade is likewise already source-address-keyed (`ip saddr
<pool> oifname != wg0`, line 329, the review #8/#5 fix) → an OVPN pool `/32` egresses for free.

Interface-keyed machinery that SURROUNDS the verdict but does NOT gate it, registered
Slice-1-adjacent (not enforcement-critical): the **MSS clamp** (`iifname wg0 oifname wg0`, line 349
— cosmetic/MTU; likely wants `tun` coverage) and the **OPEN-build mesh accepts** (line 400,
`iifname wg0` — the `pol.Mesh` path, NOT the enforcing path B1 tests). Consequence for the cut:
Slice 1 is mostly **RED (proof), not FIX** — the boundary is already address-adjudicated, exactly
what the load-bearing finding predicted.

## Mesh mode-gap (D-S9.1-6 consequence) — PROMOTED to Slice 3, verified now

The enforcing path is address-keyed (free). The **mesh path is a SEPARATE render branch**
(`pol == nil || pol.Mesh`, `egress_linux.go:399`) and **IS interface-keyed** — both blanket
accepts are `iifname wg0` (line 400):

```
iifname "wg0" oifname "wg0"   counter accept     # device↔device / spoke↔spoke
iifname "wg0" oifname != "wg0" counter accept    # spoke→egress
```

D-S9.1-6 ships the **open edition** with an OVPN server but NO policy engine → the open edition
runs the **mesh path**. An OVPN client arrives on `tun` (≠ `wg0`) → matches NEITHER blanket accept
→ its spoke↔egress and device↔device traffic is **structurally DROPPED — not a policy denial, a
mode gap.** B1 tests the enforcing path and comes back free; the open edition would ship an
OpenVPN server whose clients reach nothing. **This is the S8.2c #5 lesson exactly** (mesh emitting
no LAN→tunnel rule while enforcing+grant did — a mode gap found on iron).

**Ruling: the mesh relaxation is SLICE 3's scope** (or its own micro-slice), shape = D-transit-1
("one rule, orientation-agnostic, keyed on what the policy names" — here, source-address / pool
membership, as the masquerade already does, not interface geometry). **Reds:** (a) open-edition
mesh + OVPN client → forwarded · (b) enterprise enforcing + grant → forwarded · (c) enterprise
enforcing + no grant → DROPPED (B1). **MSS clamp stays genuinely peripheral** (cosmetic/MTU) —
REGISTERED with trigger = first OVPN MTU complaint OR the box-walk showing fragmentation.

## Slice 1 — SUBSTITUTES ≠ SATISFIES (the wire proof is OWED, not discounted)

A live-client B1 red cannot precede a live server (honest sequencing). So Slice 1's code reds are a
**named SUBSTITUTE; the wire proof is OWED with a NAMED trigger.**

- **Red (i) — compiler transport-agnosticism:** SATISFIED at unit (pure data equality — the
  compiler `Device{ID,owner,node,address}` has no transport field; the AllowEntry is keyed by the
  `/32`). Slice 1 LOCKS this as a regression guard so a future OVPN slice can't add a transport
  branch.
- **Red (ii) — chain adjudicates by address:** **RENDER-SATISFIED at unit only.** The test harness
  stubs `m.apply` (no nft/netns in CI — `egress_policy_test.go:24`), so the unit red asserts the
  rendered enforcing ruleset SHAPE (grant line = `ip saddr … ip daddr … accept`, no `iifname`; an
  ungranted pool `/32` renders to the drop tail only). It does **NOT** construct a real `tun`
  ingress or prove kernel packet fate — the harness cannot inject at the chain's real netfilter
  entry. **Per the founder's condition, this is stated plainly and the walk carries the packet-fate
  weight.**
- **OWED to the wire (trigger = the S9.1 box-walk, after Slices 2–3):** a real OpenVPN Connect
  client, org `enforcing`, zero grants → traffic **DROPPED byte-for-byte like WireGuard**; add one
  grant → flows. This DISCHARGES the substitute explicitly (recorded here so it can't discharge
  quietly). Plus the mesh reds (a)/(b) on the wire in the open edition.

## Slice cut (proposed — B1 red first; founder's ordering, one sharpening)

Agreed with the founder's ordering; one honesty sharpening on Slice 1's form (below).

1. **Slice 1 — the B1 enforcement-boundary proof, IN CODE.** Two reds, neither needing a running
   openvpn server: (i) **compiler transport-agnosticism** — an OVPN `Device` and a WG `Device` with
   the same `/32`/owner/node compile to the byte-identical `AllowEntry` set; (ii) **forward chain
   adjudicates by address** — a synthetic pool `/32` "as if from `tun`", enforcing + zero grants →
   the rendered nft ruleset DROPS it (no `iifname` exemption exists — verified above); add one grant
   → accept. **Sharpening:** the *live-client* wire form of B1 (a real OpenVPN Connect client,
   enforcing, zero grants, DROPPED byte-for-byte) **cannot precede the server that makes a client
   connectable** — it necessarily rides the box-walk after Slices 2–3. Slice 1 proves the boundary
   **in code**; the walk proves it **on the wire.** This keeps the founder's discipline exactly —
   prove the boundary before building on it — while being honest a live-client red can't come before
   a live server. (Open items for Slice 1's neighborhood: MSS-clamp `tun` coverage; leave the
   open-build mesh path as-is — B1 is an enforcing-path guarantee.)
2. **Slice 2 — the OVPN client CA + PKI + issuance** (D-S9.1-1): separate CA (own storage/sealing
   mirroring `agentca.LoadOrCreate`), CSR→leaf issue, serial recorded for the CRL.
3. **Slice 3 — agent-owned openvpn server lifecycle + CCD/`ifconfig-push` allocation + MESH
   RELAXATION** (D-S9.1-2 / D-S9.1-3 / mesh mode-gap): managed reconcile target; `server`/
   `ifconfig-pool` DISABLED, per-client `ifconfig-push` via `client-config-dir` so Tunnex's
   allocator stays the single authority; co-terminate on the gateway (D-S9.1-4) so `tun` packets
   hit the Slice-1 forward chain; **relax the mesh path off `iifname wg0`** (D-transit-1 shape,
   source-address keyed) so open-edition OVPN clients forward — reds (a)/(b)/(c) above.
4. **Slice 4 — `.ovpn` profile export + the download ceremony** (feeds S9.2; per-OS import + QR).
5. **Slice 5 — revocation full-sweep + CRL reconcile** (B2): cert-revoke + CRL push (data-plane
   desired state, agent reconciles) + address release + status clear, as ONE sweep — parity with
   `devices.Revoke`, extended by the CRL member.
