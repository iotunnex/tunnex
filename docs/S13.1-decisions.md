## Acceptance criterion — ONE QUESTION

**How does a gateway come back?**

Not a story list, and deliberately not five separate fixes. The EPIC 11 walk found **six walls** standing in front
of that single question. Each is individually small; together they mean the product cannot do the most routine
thing an operator will ever ask of it. The epic is done when a gateway that was switched off, rebuilt, lost, or
replaced comes back — **as itself**, with its site binding, its users, and its identity — by a documented
procedure that works the first time.

**The argument for the whole epic, in one line:** on the EPIC 11 walk, recovering a gateway that had merely been
**switched off** cost four hand-run steps, a wrong host, a volume pinned by a container that exited six days
earlier, and an undocumented deletion. `docs/self-host.md` describes it as *"one pasted command."*

**BETA-BLOCKING** (founder-ruled at EPIC 11 close). Not because a mechanism is broken — every mechanism works —
but because *"a site was down over a long weekend, now it needs manual re-enrolment and all its users need new
configs"* is a support burden and a trust problem, and it is the ordinary case rather than the exotic one.

## Verify pass — the six walls, with evidence

Enumerated from the EPIC 11 walk record (`walk-artifacts/S11/walk-record.md`) and re-confirmed against the code
at `f9b2dfd`. Every claim below cites what establishes it, because the walk's own lesson was that a check which
cannot fail proves nothing.

### Wall 1 — the certificate is dead and cannot be renewed (WF-S11-6, HIGH)

`agentca.CertTTL = 48 * time.Hour`. The agent renews at half-life via `POST /agent/renew`, and the agent listener
is `ClientAuth: tls.RequireAndVerifyClientCert` for **every** route including `/agent/renew`
(`agentchannel.go:55`, `:68`). So the expired certificate is rejected during the TLS handshake, before any handler
runs: **the only endpoint that can issue a new certificate requires the certificate that expired.**

`control/client.go:117` states the unstated precondition out loud — *"Renewing at half-life keeps the agent from
ever reaching cert expiry"* — which holds for a **continuously running** agent and fails silently for any other
kind.

*Wire evidence:* `aws-gw-1`, off Jul 25 → Jul 30, looped for five minutes on
`remote error: tls: expired certificate` with no path out.

### Wall 2 — the name is held forever (WF-S11-8, HIGH) — **PARTLY SHIPPED**

`nodes_org_id_name_key` was an **unconditional** unique index on `(org_id, name)` and there is no delete
endpoint — only `revoke`, which sets `status='revoked'`. A revoked row therefore held its name permanently and
`CreateNode` answered `409 node_exists` (`service.go:277`).

**Migration 0056 (shipped in EPIC 11) replaced it with `UNIQUE (org_id, name) WHERE revoked_at IS NULL`**, so a
revoked gateway frees its name. *Wire evidence:* `aws-gw-1` re-enrolled under its own name while the revoked row
still held it. **This wall is down** — but see Wall 3: the gateway that came back was not the same gateway.

### Wall 3 — identity does not survive a rebuild (WF-S11-8(b), HIGH)

A re-enrolled gateway is a **new node**: new `id`, and therefore an **orphaned site binding**, a fresh metrics
series, and every runbook/dashboard/alert reference pointing at a dead row.

*Wire evidence, side by side:*

```
   name   | status  |               site_id                | applied_hash
 aws-gw-1 | revoked | 019f8e4a-2664-7a7c-9671-790ff28a240b | 152716a5fa58
 aws-gw-1 | active  |                                      | df87259122ac
```

The Sites page then rendered `aws-site` as **"2 gateways"**, both dead, while the live, healthy,
artifact-applying gateway sat outside the site entirely.

### Wall 4 — the agent discards a valid join token (WF-S11-11, HIGH)

Handed a freshly minted valid token, using the command the product itself generated, on the correct host, the
agent logged `agent_reusing_stored_identity`, **discarded the token**, and resumed the expired certificate. A
`WARN`. It never says the token was thrown away.

`main.go:82` records why the precedence exists — S8.2c WF-2, where a re-used VM silently kept its old identity and
org and mis-convicted D2 during the cross-cloud walk. **Preferring the stored identity is deliberate and
correct**; nobody considered the stored identity being *dead*, so a diagnostic for one problem now papers over an
unrecoverable one.

Compounding: the documented workaround (wipe the state volume) **itself failed** — a container that had exited six
days earlier still pinned it, `docker volume rm` refused, and the agent reused the dead identity a third time. Two
layers of silence over one unrecoverable state.

**WF-S11-11b** rides here: `nodeName` comes from `TUNNEX_NODE_NAME` and is never updated from the stored cert's
CN, so the reuse warning prints the name **requested** rather than the identity **kept**. Observed live: run on
the wrong host, it printed `node_name: aws-gw-1` while reusing *azure-gw's* certificate. The diagnostic that
exists to reveal which identity is kept names the one that is not.

### Wall 5 — a revoked gateway keeps its site binding and still reaches the policy compiler (WF-S11-14, MED-HIGH)

Two queries feed related decisions about a site's gateways and only one filters revoked rows:

```sql
-- sites.sql:77 — hub-set / election input — FILTERS
WHERE org_id = $1 AND site_id IS NOT NULL AND wg_public_key <> '' AND status = 'active';
--   its own comment: "Revoking a gateway drops it here → ... (no blackhole)"

-- sites.sql:85 — ListSiteNodesForOrg, the S8.2 POLICY COMPILER input — DOES NOT
WHERE org_id = $1 AND site_id IS NOT NULL;
--   its own comment: "places a src_kind='site' grant on the src + dst gateways AND the transit HUB"
```

And `Revoke` is explicit that it leaves the binding: *"RevokeNode leaves site_id set"* (`service.go`, pre-revoke
read comment). So a revoked gateway remains a site binding, visible to grant placement and transit-hub
designation, while hub election has already dropped it.

**Not yet traced:** whether the compiler's hub designation actually diverges from the hub-set election in
practice. What *is* established is the asymmetry, with revocation as the trigger.

### Wall 6 — recovering a gateway does not recover its USERS (found in THIS verify pass, HIGH)

`Revoke` cascades:

```sql
-- RevokeDevicesForNode
UPDATE devices SET status = 'revoked', revoked_at = now(), assigned_ip = NULL
WHERE node_id = $1 AND status IN ('active','pending') AND deleted_at IS NULL;
```

plus `RevokeOVPNClientCertsForNode`, a hub-set re-election, and a CRL rebuild.

**Every device homed on a revoked gateway is revoked and its address freed.** So the recovery procedure, followed
correctly and to completion, yields a working gateway with **zero users** — and because device configs are
one-time secrets, every user must be re-enrolled and re-issued a WireGuard config by hand.

This is the most severe wall for a real deployment and it was not in the walk's finding list: the walk's rig had
no devices on the gateway it recovered. **A verify pass found it before an operator did**, which is the argument
for doing one.

*Not yet established:* whether device revocation is reversible (a `revoked` device row still holds its
`public_key`; whether un-revoking is coherent with the identity↔credential binding is a **decide-item**, D5).

## Carried in from EPIC 11 — already RULED, restated so this paper is self-contained

### WF-S11-11 → **(a)**, with the determination condition

Prefer the join token when the stored identity is **unusable**. The stored identity exists to prevent accidental
re-enrolment of a *working* node; when it is provably unusable, deferring to it converts a safety feature into a
deadlock.

**Condition: "unusable" must be a DETERMINATION, not an assumption.** The agent cites what makes it so — expired
(`NotAfter` in the past), unreadable (parse failure), or mismatched (CN ≠ requested node name) — and **fails
toward the stored identity when uncertain**. An agent that guesses "probably dead" on a transient read error would
turn a diagnostic into a self-inflicted identity change. Log the determination *and its evidence*, not just the
outcome.

Folds with **WF-S11-11b**: read the stored certificate's CN, print stored **and** requested, escalate when they
differ — a mismatch is itself the interesting signal (a reused VM image, or an enrolment aimed at the wrong host).

#### REFINEMENT, ruled during Slice 1: a mismatch is NOT a determination of "unusable"

The condition as first written listed three determinations — expired, unreadable, **name mismatch** — and the
third was wrong. Expired and unreadable are proofs the credential **cannot function**; a mismatch is a proof that
**configuration disagrees**, which is not the same thing.

The counterexample is in the walk that produced the ruling: on `azure-gw`, holding `azure-gw`'s **valid**
certificate, with `TUNNEX_NODE_NAME=aws-gw-1`, a mismatch-authorizes rule would have abandoned a live gateway's
identity and enrolled that host as a different node — the S8.2c WF-2 disaster **reproduced by the guard meant to
prevent it**.

**RULED:** a mismatch on a still-valid certificate is a **loud ERROR and never an authorization**. The
fail-toward-the-stored-identity clause governs, which is why it sits in the same sentence. Mismatch *and* expired
does authorize, because then nothing is being protected. Minted as a law: *a determination of "gone" must prove
the credential cannot work, never that configuration disagrees* (`docs/laws.md`) — and it binds D3 identically:
`revoked` or `cert_not_after < now()` may authorize; `last_seen_at` stale may not.

### WF-S11-14 → **(c)**, both halves

- **Filter the compiler input** — `ListSiteNodesForOrg` gains `status = 'active'`, matching its sibling. The
  **shared-seam fix**: a revoked node leaking into compiler input is the identity-binding invariant's fourth
  consumer problem, so filtering at the input fixes every consumer at once.
- **Unbind on revocation** — `site_id = NULL` joins the sweep, stopping the stale binding at source and making
  both queries agree by construction.

Both, not either: the filter protects against any future producer of a stale binding; the unbind removes the one
that exists. Needs a fixture red proving a revoked gateway receives **no placement** and is **never designated
hub**, plus a re-run of the site-transit legs.

*Interaction with D2, flagged:* if identity survives a rebuild (replace-in-place), unbinding on revocation may be
the wrong default — a replaced gateway wants its binding **transferred**, not cleared. D5 resolves the ordering.

### The re-key security guard — DRAFTED at EPIC 11 close, to be locked here

*"A join token pinned to an existing node re-keys that row"* must not become a **credential swap on a live node**.
Unguarded it is a takeover primitive: mint a token, re-key a healthy production gateway, and the attacker's agent
inherits its identity, its site binding and its policy while the real gateway is silently displaced.

**The guard: re-key is permitted ONLY against a node the control plane can itself verify is gone** — `revoked`,
or cert-expired-and-unreachable (`cert_not_after < now()`, CP-recorded since 0054/0055) — and **never against one
currently reporting**. The check lives on the **server**; it can never be a client-supplied flag.

Two further conditions already recorded:

1. **Revocation must still win.** Re-key must not resurrect a node an operator deliberately revoked without that
   being an explicit, audited act — otherwise re-key becomes an un-revoke, and revocation is the product's
   security primitive.
2. **The audit trail must show a succession, not a mutation** — one node whose credential changed, with cause and
   actor, so *"this gateway was rebuilt on the 4th"* is answerable later.

## Decide-items — HELD, with leans

### D1 — What authenticates a returning gateway when its certificate is dead?

The core question. Options:

- **(a) The existing join token, with the agent-side fix only.** WF-S11-11(a) already makes the agent prefer a
  token over a dead identity, so recovery becomes: mint a token, paste the command. No new credential, no new
  schema. But the operator must **be present** — a gateway cannot recover unattended, and a fleet of fifty
  bricked gateways is fifty console visits.
- **(b) A durable per-gateway re-enrolment credential**, minted at first enrolment and stored alongside the
  cert — long-lived, hash-stored, fingerprinted, revocable, mirroring `machine_credentials` (0052). The agent
  presents it to a dedicated re-enrolment endpoint when its cert is unusable. **Unattended recovery becomes
  possible**, and the credential is exactly as revocable as the node.
- **(c) Proof-of-possession of the existing keypair.** The agent still holds the private key matching the public
  key the CP has on record; it signs a challenge, and the CP issues a new certificate to the holder of the key it
  already knows. **No new secret at all** — the strongest option on paper, since it introduces no material to
  leak.

**RULED: (c) as the mechanism, with (a) as the always-available manual path.** (c) is the smallest trust
expansion — the CP already trusts that public key, so proving possession of its private half is not a new grant,
it is the *same* grant re-attested. It also composes with D3's guard for free. (a) must remain regardless: a wiped
state volume loses the key too, and only a fresh token recovers from that.

#### The security delta, stated rather than denied

A reviewer will ask whether PoP-after-expiry weakens the 48-hour compromise bound. It mostly does not, and the
part that does is worth naming precisely — *"we assumed it was equivalent"* is a worse answer than a stated delta.

**Why there is almost no delta.** PoP of the existing keypair proves possession of the **state volume**.
Certificate renewal over mTLS proves *the same thing*: the client key lives in that volume, and the certificate is
useless without it. A thief holding the state volume **can already renew today**, inside the 48-hour window, using
the exact material PoP would ask for. So PoP-after-expiry grants an attacker nothing they did not already have
while the certificate was live — it removes an arbitrary time bound on the **legitimate operator**, not on the
thief.

**What the 48-hour bound actually buys.** It bounds the window in which a stolen-**and-then-revoked** credential
stays usable. But revocation already handles that case directly and better: the CP refuses a revoked node
regardless of what it proves. So the bound's real contribution is narrower — it limits exposure from a **silent
theft nobody detected**.

**That is the honest delta: PoP-after-expiry extends the silent-theft window from 48 hours to indefinite.** Small,
but real. Not dismissed — mitigated, twice:

1. **D3's gate** — PoP is permitted *only* against a node the CP believes is gone (`revoked`, or
   `cert_not_after < now()`). A live, reporting gateway cannot be re-keyed at all.
2. **A loud, audited succession** — recovery records the **old and new key fingerprints**, the actor, and the cause.

**Net posture improves.** A silent thief using PoP produces an audit row an operator can see. Today's silent thief
renewing over mTLS produces **nothing at all** — indistinguishable from the real gateway doing its job. The change
trades an unenforced time bound for a detectable event, which is the better trade.

### D2 — Does identity survive a rebuild (replace-in-place), or does a new node inherit the binding?

- **(a) Replace-in-place** — a token pinned to an existing node **re-keys that row**: same `id`, same `site_id`,
  same history, same metrics series, new cert serial and new WG key. The gateway that comes back **is** the
  gateway that left.
- **(b) New node, inherit the binding** — enrolment creates a new row and an explicit *transfer* moves
  `site_id`, `hub_priority` and device homing across.

**RULED: (a).** It is what an operator means by "the gateway came back", and (b) reintroduces every consequence of
Wall 3 with extra machinery to paper over it — two rows, a transfer step that can half-apply, and a metrics series
that still breaks. (a) is a bigger change to the enrolment path and it is the honest one.

**Conditions if (a) is ruled:** the WG **public key changes** (the agent generates locally and must, since the old
private key may be compromised or gone), so every peer's `AllowedIPs` and every site link must reconcile — that
is a full-sweep push, not a field update. And re-key must be **atomic**: a row that is half-re-keyed is a gateway
whose cert says one thing and whose peers say another.

### D3 — What proves the original is gone before a re-key is permitted?

The guard drafted above, made precise. The CP's available evidence, all already recorded:

| evidence | strength |
|---|---|
| `status = 'revoked'` | **strongest** — a human decided |
| `cert_not_after < now()` (0054-stamped) | strong — arithmetic on our own signing record |
| `cert_not_after` backfilled bound (0055) | strong, and cannot false-positive by construction |
| `last_seen_at` stale | **inadmissible alone** — silence has many causes; this is the inference the whole EPIC 11 walk taught us to refuse |

**RULED: `revoked` OR `cert_not_after < now()`, and nothing else.** Never `last_seen_at`. Never a client-supplied
assertion. And if D1 lands on (c), possession-of-the-original-key is *additional* evidence that composes with
this — not a substitute for it, because possession does not prove the original stopped running.

**Explicitly refused:** any operator-supplied "force" flag. A guard that can be overridden by the party most
motivated to override it is documentation, not a guard.

### D4 — The name-reuse census: does every query disambiguate by id, not name?

Migration 0056 made duplicate names possible among revoked rows. EPIC 11's census found **one** name-keyed query
(`GetNodeByOrgName`, now filtered to active), no SQL join on `nodes.name`, no Go-side by-name resolver, and
identity resolution going through `cert_serial`. `TestNoAmbiguousNodeNameLookups` guards it.

**That census covered LOOKUPS. It did not cover:**

- **Pickers** — the hub-pin list rendered one `aws-gw-1` with no indication which of two same-named rows it was.
  A human choosing between two identical labels is a surface the census never considered.
- **Displays** — any list, badge, audit line or log field that shows a node name without its status or id.
- **Operator inputs** — the join-token `node_name` pin, and anything else that accepts a name as an identifier.

**RULED: extend the census to all four surfaces before shipping anything else in this epic**, and make it a
*decisions* census rather than a *presence* census — for each surface, state what it does when two rows share a
name. This is the ledger item registered at EPIC 11's close, and this epic is where it comes due.

### D5 — What does recovery restore, and is device revocation reversible? (Wall 6)

The hardest scoping question, and the one the verify pass added.

- **(a) Recovery restores the gateway only.** Devices stay revoked; users re-enrol. Honest, and makes a single
  gateway rebuild a fleet-wide user event.
- **(b) Recovery un-revokes the cascade.** Devices homed on the recovered node return to `active` with their
  addresses re-assigned. Restores service, but **un-revoking is a security operation**: a device revoked
  deliberately (a lost laptop) must never return because its gateway was rebuilt.
- **(c) Distinguish the CAUSE of revocation.** A device revoked *by cascade* is restorable; one revoked
  *deliberately* is not. Requires recording why (`revoked_cause`), which the schema does not have today.

**RULED: (c) — record the CAUSE, and that column IS Wall 6's fix.** A device revoked *because its gateway was* is restorable; a device revoked *on purpose* never is. It is the only option that is both safe and useful, and the distinction is real rather than
bookkeeping — "we revoked this because its gateway went away" and "we revoked this because the user lost the
laptop" are different facts that currently render identically. Note this also **decides D2's ordering** with
WF-S11-14(c)'s unbind: if replace-in-place is ruled, revocation should unbind but recovery must be able to
*restore* the binding, so the binding's history has to survive the unbind.

**Open sub-question, held:** whether address re-assignment on restore can collide with an address handed out
meanwhile. The pool is org-scoped and `assigned_ip` was freed — so restore must re-allocate, not re-claim, and a
device's config (which embeds its address) may therefore be stale on return. That interacts with the
`needs_reexport` surface S9.1 already ships.

### D6 — Slice cut and what proves it. CONFIRMED as leaned.

1. **Agent-side identity precedence** (WF-S11-11(a) + 11b) — smallest, unblocks manual recovery immediately, and
   independent of every other decision.
2. **The revoked-node seam** (WF-S11-14(c), both halves) — filter + unbind, with the fixture red.
3. **D4's extended census** — before any new identity machinery, since it constrains what displays and pickers may
   assume.
4. **Re-key / replace-in-place** (D1 + D2 + D3) — the epic's core, with the security guard as its first red.
5. **Cascade restore** (D5) — last, because it depends on 4's identity semantics.
6. **Docs + the walk** — `self-host.md`'s recovery sentence rewritten to a procedure that has actually been run,
   and a walk whose teeth are: *switch a gateway off for longer than 48h, bring it back, and have it return as
   itself with its users* — zero hand-run steps.

**The walk's acceptance is the sentence that started this epic.** If the procedure still needs an undocumented
volume deletion, the epic is not done.

### S13-1 (HIGH) — every new device was homed on `nodes[0]`, revoked or not

`ListNodes` returns **every** node in the org ordered by `created_at`. So on any deployment whose **oldest gateway
had been revoked**, every device created afterwards was homed on a dead gateway — and issued a **one-time**
WireGuard config that could never connect. A one-time secret cannot be re-issued, so the failure burns the
artifact rather than merely inconveniencing the user.

**The EPIC 11 walk's own fleet was in exactly that state:** `aws-gw-1` was revoked and had the earliest
`created_at`, so it *was* `nodes[0]`.

And the same page's sibling surface got it right — `Sites.tsx` filters to active before offering a gateway. Two
consumers of one list, one of them remembering: **the identical asymmetry as WF-S11-14**, at the UI tier.

**Sixth instance of guard-not-mirrored across four epics — and this one sat in a file ADJACENT to the one that got
it right.** `Sites.tsx` and `Devices.tsx` are siblings, both consume the same `nodes` array from the same page load,
and only one filtered. **Proximity does not propagate correctness.** A convention held in one file is not held by
the file next to it; only a shared function or a census makes it hold. That is why the rule now lives in
`src/lib/nodepick.ts` rather than as a filter repeated at each call site.

Fixed by extracting the rule to `src/lib/nodepick.ts` — `selectableNodes`, `defaultDeviceNode` (returns **null**
rather than falling back, because refusing is the recoverable direction), and `nodeLabel`. The empty-state hint now
distinguishes *no gateway enrolled* from *every gateway revoked*, because the remedies differ.

## Slice 4 decide-items, surfaced mid-build and RULED

### D7 — the CP stored nothing PoP could verify against. RULED (a).

`nodes` held `cert_serial`, `wg_public_key`, `cert_not_after` — and **no mTLS public key or certificate**. So a
signature had nothing to verify against, and D1(c) as ruled could not be implemented.

`wg_public_key` cannot substitute: **WireGuard keys are X25519, for Diffie-Hellman, and cannot produce signatures.**
Arithmetic, not policy.

**RULED (a): store the mTLS public key** (migration 0057, `nodes.cert_public_key`, base64 SPKI DER — the form
`x509.ParsePKIXPublicKey` reads back, so verification never guesses an encoding). (b), storing the certificate PEM,
was rejected: the audit artifact it buys is reconstructible from the serial plus the CA's records, and it
duplicates what the agent already holds.

**COVERAGE IS A PRODUCT LIMITATION, stated not footnoted.** PoP recovers only nodes whose key the CP has recorded.
Every node enrolled before 0057 has none, and falls back to the join token.

- **Stamped at RENEWAL as well as enrolment** — that is what makes coverage arrive within one renewal cycle
  (~24h at half-life of a 48h certificate) rather than only for new enrolments. A running fleet self-heals into
  coverage; only already-dead nodes stay token-only, and those are exactly the ones a human is already attending to.
- **Distinguishing "recoverable by PoP" from "token-only" on the health surface: REGISTERED, not built.** It is
  derivable (`cert_public_key IS NOT NULL`) but it needs an OpenAPI field, a generate cycle, and a consumer census
  — and the epic has already established that adding a surface without censusing its consumers is how WF-S11-7 and
  WF-S11-10c happened. It rides the recovery-status surface work rather than being bolted on here.

### D8 — the re-key endpoint lives on the PUBLIC API listener. RULED explicitly.

`ClientAuth` is a property of the **listener**, not the route; Go offers no per-route relaxation. An expired
certificate fails the TLS handshake before any handler runs, so re-key cannot live beside `/agent/renew`. It goes on
the public API listener alongside `/agent/enroll`, which is already public on the stated principle that *"the join
token is the credential."*

**In its starkest form, in our words rather than a reviewer's:**

> **Re-key is an unauthenticated endpoint. Its entire defence is (i) D3's gone-gate and (ii) the proof-of-possession
> signature.** There is no session, no bearer token, and no client certificate — by construction, since the caller's
> certificate is the thing that has failed.

Conditions, all ruled:

- **Rate-limited** (S11.3's machinery).
- **The gone-gate is evaluated BEFORE any cryptographic work**, and the mechanism is worth stating rather than
  restating: RSA signature verification is the expensive, timing-visible step in the handler; the gate is a field
  comparison. Verify first and response latency differs measurably between *"this serial belongs to a live gateway"*
  and *"…to an expired one"* — a fleet liveness oracle for anyone who can reach the API. **Cheap gate first makes
  every refusal cost the same.**
- **Uniform refusal**: a live node, a nonexistent node, a malformed proof and a wrong-key proof are
  indistinguishable in the response. `rekey.ErrProofInvalid` is a single undifferentiated error for this reason;
  detail goes to the log, where an operator can see it and an attacker cannot.

### D9 — challenge-response, keyed on the certificate SERIAL. RULED.

The agent fetches a nonce, then submits its new CSR plus a signature over **(nonce ‖ CSR DER)**. Both hazards are
real and the binding must cover both:

- **Binding** — without the CSR in the signed message, a proof captured from a legitimate exchange pairs with an
  attacker's own CSR, and a caller who never held the key gets a certificate for the node.
- **Replay** — binding alone still permits replaying the whole captured request, so the nonce is **server-issued,
  single-use and short-lived**.

**Keyed on the serial, not the name.** A name-keyed challenge endpoint is a **name-enumeration oracle**, and node
names are guessable in a way serials are not. The challenge endpoint leaks nothing about whether a serial exists —
the same uniform-refusal rule as D8.

### The reds, and what mutating them taught (again)

`internal/rekey` ships with the verification primitive and seven reds before any route exists. All four mutations
reject:

| mutation | outcome |
|---|---|
| drop the CSR from the signed message (breaks binding) | ✅ "a proof must NOT verify against a different CSR" |
| drop the nonce from the signed message (breaks replay protection) | ✅ "must NOT verify under another" |
| explicitly accept an empty recorded key | ✅ "'I cannot check' must never resolve to 'it is fine'" |
| neutralise the CSR self-signature check | ✅ "must be refused, even when the proof of possession is valid" |

Two needed redoing, and both are the corollary earning its keep:

- The first attempt at the empty-key mutation (`if false { return nil }`) left the case refused by a **second**
  path — base64/parse failure. That is **defence in depth, not a blind guard**, and the distinction matters: the
  mutation was benign rather than revealing. The real vulnerability shape (explicitly returning nil) is rejected.
- The CSR-signature mutation **build-failed twice** on an orphaned `err` before a compiling form was found. A
  mutation that does not compile tests nothing, and its output is indistinguishable from a pass.

## D3 AMENDED mid-build — PoP re-key is authorized by EXPIRY ONLY

The original D3 listed **two** authorizing evidences: `revoked` and `cert_not_after < now()`. Writing `RekeyNode`
forced the question, because re-keying a revoked node must restore `status='active'` or the gateway comes back and is
still refused. **So re-key of a revoked node IS an un-revoke** — and re-key is authenticated only by proof of
possession.

### The attack the original ruling permitted

1. An attacker steals a gateway's state volume, which is its **private key**.
2. The operator notices and **revokes** that gateway — the product's answer to a stolen credential.
3. The attacker calls re-key, proving possession of the stolen key.
4. `revoked` authorizes it.
5. The attacker holds a **fresh certificate for that node id** — active, same site binding, same policy.

**Revocation defeated by the exact credential it was invoked against.** And the paper already forbade this, in a
condition on the same page — *"re-key must not become an un-revoke; revocation is the product's security
primitive."* **The evidence list contradicted a condition in its own document. The condition was right and the list
was wrong.**

### Why the two evidences are not equivalent

`revoked` looked like the *stronger* authorization because it is the strongest evidence a node is **gone**. That
conflated strength-of-evidence-that-it-is-gone with validity-of-authorization-to-**return**.

> **EXPIRY IS AN ABSENCE OF ACTION; REVOCATION IS THE PRESENCE OF A DECISION.** A cryptographic proof may overturn
> the first and must never overturn the second — because the proof cannot distinguish the legitimate holder from
> whoever took the key, and revocation is precisely the response to that ambiguity.

Minted as a law (`docs/laws.md`), because it generalizes past this endpoint to every future "prove you are still
you" mechanism.

**RULED: expiry only.** A revoked node recovers exclusively via an operator-minted join token — a human act, which
is the right gate for undoing a human decision.

### The mechanism simplification is the ruling's payoff

`RekeyNode` now **does not mention `status` or `revoked_at` at all** — not "sets them carefully", does not reference
them. Re-key is therefore **incapable** of resurrection rather than forbidden from it, the same instinct as
`RekeyAuthorized` having no liveness parameter to pass. It is additionally guarded on `status = 'active'` in the
WHERE clause, so a revoked row is refused even by a caller that reached the query without the gate.

`TestRekeyQueryCannotResurrect` enforces both halves against the query text, comments stripped — the prose explains
the reasoning and names both columns, and matching prose would be matching a coincidence of the text rather than the
property. Proven to reject: reintroducing `status = 'active', revoked_at = NULL` fails with
`must NOT write "status"` and `must NOT write "revoked_at"`.

### The inverted reds, recorded rather than quietly edited

Two assertions reversed meaning, and both now carry the attack chain in the test itself — a future reader who sees
*"revoked → refuse"* without the chain will eventually decide it is an inconvenience worth relaxing:

- `TestRekeyAuthorizedOnlyByTheTwoRuledEvidences` → **`TestRekeyNeverUnRevokes`** + `TestExpiryIsTheONLYAuthorization`.
- `TestUnknownExpiryIsNotGone`'s tail asserted "revocation authorizes regardless of what is known about expiry — it
  is an independent evidence." It **is** independent evidence the node is gone, and simultaneously evidence that a
  human wanted the key-holder locked out, which is exactly what a proof of possession cannot adjudicate.

### Uniform refusal on the revoked path (ruled condition)

The revoked refusal is **indistinguishable** to a caller from not-found, live-node, and bad-proof. `RekeyAuthorized`
returns its reason **for the log only**; an attacker probing with a stolen key must not learn
revoked-versus-not-found-versus-live. The remedy goes in the operator-facing docs and the health surface, never in
the endpoint's response.

### The challenge store (D9)

Migration 0058, `node_rekey_challenges`: 32 random bytes, bound to the serial asked about, expiring, consumed once.
**Issued without checking the serial exists** — a challenge that succeeded only for real serials would be the
enumeration oracle D9 exists to avoid, so the submit step is where a nonexistent serial fails, with the same uniform
refusal. Single use is enforced by the UPDATE's own WHERE clause rather than a read-then-write, because two
concurrent submits with one nonce must not both win.

All three new queries were caught by the org-scoping lint and each carries a **justified** cross-org annotation
rather than a blanket one: challenges have no org and cannot (they precede knowing the caller), and `RekeyNode` is
authorized by the globally-unique serial plus PoP — the same reasoning that already annotates `GetNodeByCertSerial`,
which is how every authenticated agent request resolves its node.

## Slice 5 — cascade restore (Wall 6, D5). BUILT, with a NAMED interim gap.

Revoking a gateway cascades to every device homed on it, so recovery without this step handed back a working gateway
with **zero users**, each needing a re-issued one-time config: one rebuild becoming a fleet-wide user event,
invisible until people called.

### What made it buildable: `revoked_cause`

`'cascade'` (its gateway went away — restorable) versus `'deliberate'` (an operator revoked this device — never
restorable). Those rendered **identically** before migration 0059, which is why restore could not be built at all:
un-revoking the cascade set would have revived a lost laptop, and refusing to un-revoke anything left Wall 6
standing. NULL — revoked before 0059 — is honestly unknown and therefore **not** restorable.

### Revocation stopped destroying the address

Both revoke paths set `assigned_ip = NULL`, so a cascade-revoked device had lost the record of what it held, making
the original unreclaimable **in principle** rather than merely in contention. **The same defect as the `site_id`
unbind reverted earlier in this epic, one column over**, and the same resolution: *revocation preserves what it
invalidates.*

Keeping it costs nothing, because the two readers that define taken-ness both filter on status —
`devices_org_ip_key` and `ListActiveDeviceAllocations` — so a revoked row holding an address neither blocks
reallocation nor reads as live.

### The ruled fork, implemented

Reclaim first, allocate second. The oracle is **asked, never inferred**: `ListActiveDeviceAllocations`, whose own
comment calls it *"the SINGLE definition of live allocation… so there are no two filtered reads to drift apart"*,
read once under the same org advisory lock device-create takes. A fresh address only when the original is genuinely
held; `device.restored_readdressed` audited distinctly when it is.

### THE HONEST INTERIM GAP — stated, not smoothed

**A device restored to a different address has no device-surface signal today.** The ruled fork's third condition —
*mark stale only in the fallback case* — **has no mechanism until Slice 6.** `needs_reexport` is derived from baked
**ranges**, and there is no `provisioned_ip` column for an address to be compared against, so a re-addressed device
renders exactly as clean as one that kept its address.

The audit event carries the fact regardless (`device.restored_readdressed`, with `surface_gap` naming this), so
**Slice 6 closes a named gap rather than adding a feature.** An operator reading the audit log can see it; an
operator reading the device list cannot, and that asymmetry is on the record rather than discovered.

> **CLOSED by Slice 6 (below).** `devices.provisioned_ip` exists, the comparison runs for every provisioning mode,
> and the `surface_gap` meta key was **removed rather than left to age into a false claim** — the audit trail no
> longer says the surface cannot show this, because it can.

### Two-layer guard, discriminated

The reclaim check is the first layer; the partial unique index is the second. A mutation removing the check did
**not** silently double-assign — the index raised `SQLSTATE 23505` instead. Naming which layer caught it is the
difference between *defence in depth* and *a blind guard nobody has noticed yet*, and both are load-bearing here.

## Slice 6 — BUILT. `provisioned_ip`, and the asymmetry it exposes

Migration `0060_device_provisioned_ip`; recorded in the **same transaction as device creation**, so a device is never
briefly indistinguishable from one issued before the column existed.

### The defect was an ASYMMETRY, not an absence

`provisioned_ranges` was recorded and compared. The **address** was neither — so `assigned_ip` had nothing to compare
against, and a device whose address changed rendered **exactly as clean** as one that never moved. Slice 5 made it
concrete: cascade-restore onto a fresh address produces a user whose config cannot connect, and the only signal was
an audit row.

The **second** half of the asymmetry is the read-time gate. `if d.Device.ProvisioningMode == "static"` excluded
managed devices from the whole signal — but every issued config embeds an interface address, managed included, so
those users were left to discover a dead tunnel by failing to connect. The mode discrimination now lives **inside**
`devices.ProfileStale`, where the ranges half stays static-only (a managed device *polls* routes, so nothing baked
can go stale) and the address half does not.

| cause | static | managed | why |
|---|---|---|---|
| baked site **routes** ≠ current routed ranges | ✅ | ❌ | only a static export bakes routes; reporting it for managed is a permanent false positive |
| baked **address** ≠ current address | ✅ | ✅ | every issued config embeds an interface address |
| snapshot **absent** (row predates 0060) | fresh | fresh | unknown is not stale — the 0055 backfill reasoning, one column over |

### One boolean, not two

`needs_reexport` gained a cause, not a sibling field. The operator-facing meaning is cause-neutral — *your config is
out of date, re-import it* — and a second mirror-surface boolean is the shape that produced two findings this epic
(WF-S11-7, WF-S11-10c: a surface added without censusing its consumers). Recorded in `ProfileStale`'s own comment so
a third cause arrives there deliberately.

### Both contract rewrites, plus one the census under-scoped

- **OpenAPI** — the sentence every generated client inherits. It promised *"Absent/false for managed (polling)
  devices"*, i.e. **the exact gating being removed**. Rewritten to name both causes, their mode scopes, and the
  unknown-is-fresh floor.
- **`Devices.tsx` tooltip** — *"predates a site-range change"* is a false explanation for a re-addressed device.
- **The badge LABEL, which the census marked ✅ cause-neutral, was not.** It read *"re-export needed"*, and
  *re-export* is not an action a managed device's owner can take — there is no export path for managed provisioning.
  Now *"config out of date"*. The census was right that the label named no cause and wrong that it named no
  **action**; a label can lie through the remedy it prescribes.

### Reds, each mutation-proven

|---|---|---|
| `TestProfileStaleAddressHalfAppliesToEVERYMode` | address half re-gated to static-only | FAIL ✅ |

## D10 — the SECOND identifier. RULED (fingerprint-identification), BUILT

Review finding #8 (lost-response) landed only its atomic half in Slice 4. The remainder was a decide-item with two
faces, ruled: **identify by key fingerprint**, not a grace window on the previous serial.

### The failure, precisely

Re-key commits the new serial and the new public key, **then** answers. If that answer is lost — dropped connection,
ingress timeout, the agent process restarting between commit and write — the control plane holds a serial the agent
never received. The agent retries with the serial from its stored certificate, **which no row carries any more**, and
is refused forever. One dropped packet costs a gateway its identity: recovery then means a join token, a NEW node,
the site binding gone, and every device homed on it re-issued.

### Why fingerprint and not a grace window

A grace window reintroduces a **time bound of exactly the kind D3 spent this epic removing** — recovery working for
an hour and then not, for reasons invisible from outside. The fingerprint is material the control plane **already
records** (0057) and the agent already holds, so it adds a *lookup key*, not a new secret. And a public-key
fingerprint is at least as unguessable as a serial, which was D9's whole criterion for choosing the serial over the
node name.

### The counter-face, answered rather than dismissed

An unauthenticated endpoint now answers to **two** lookup keys, so the uniform-refusal discipline has to hold across
both. It does, and it is red'd: unknown serial · unknown fingerprint · **ambiguous** fingerprint · live node ·
wrong key · unknown identifier kind all return the SAME refusal, compared as a value rather than as "an error"
(`TestBothIdentifiersRefuseIndistinguishably`).

### Uniqueness — the founder's addition, settled

If two nodes could present the same recorded key material the lookup is ambiguous at the moment it is being trusted.
Both offered resolutions were acceptable; **ruled: defined refusal, not a constraint.**

- Nothing today prevents two nodes enrolling with the same key (copy a state directory, mint a second token), so a
  UNIQUE index would turn a lookup ambiguity into a **migration failure** on any fleet where that already happened,
  and later into a confusing enrolment refusal on a legitimate operation.
- So the query is `:many … LIMIT 2` and its caller **refuses when it gets more than one**. Deliberately not `:one`,
  which would have raised a runtime "multiple rows" error — a refusal by accident, distinguishable in timing and in
  the log from a clean one.
- The duplicate node stays recoverable **by its own serial**, and the log names the ambiguity with a remedy. Both
  halves asserted.

### Exact match, and the shape question it raised

`=` on the full 64-hex digest. Never a prefix — a prefix match is an enumeration primitive that reports *warmer* —
never case-normalised, never trimmed. Refused shapes return the **uniform refusal**, not a 400: the OpenAPI schema
deliberately carries **no pattern and no length constraint**, because a schema violation would answer 400 where an
unknown identifier answers 403, and that difference tells a prober how far they got.

### Three implementations of one digest, pinned to one golden vector

The identifier is SHA-256 over the **SPKI DER** (not over the base64 text: a key's identity must not depend on how it
was written down). It is computed in three places that cannot import each other:

| # | where | role |
|---|---|---|
| 1 | `control.KeyFingerprintFromSPKI` (agent module) | computes what is SENT |
| 2 | `nodes.KeyFingerprint` (api module) | the audit/log prefix |
| 3 | `nodes.cert_key_fingerprint`, a **GENERATED** column (0061) | what the lookup MATCHES ON |

(1) and (3) are load-bearing, and if they drift, re-key-by-fingerprint matches nothing — a failure indistinguishable
from *this gateway cannot be recovered*. Two Go modules and one SQL expression cannot share code, so they share a
**golden vector** asserted in all three, including against the generated column in an integration test. The vector is
a **public** key, so no private material enters the repository to prove it.

The column is **generated by the database** rather than written by application code, so it cannot drift from the key
it names — there is no path that updates one without the other.

**A stated redefinition:** the audit's `old_key_fingerprint` used to digest the base64 text; it now digests the DER,
so it is a 12-hex **prefix of the identifier** and an operator can match the two. Fingerprints in audit rows written
before this change are not comparable with ones written after.

### The agent half — persist before submit, and CONVERGE

The fingerprint is only usable if the agent still holds the key the control plane recorded, so the pending keypair is
**written to disk before the request goes out** (`rekey-pending-key.pem`, 0600, temp-then-rename), and **reused
across attempts**. Reuse is the correctness property: a fresh key per attempt would walk the identity forward every
time, leaving the agent proving possession of something the control plane never saw — the same brick by a longer
route. Retries re-assert one identity instead of starting over.

A separate filename, not an early write to `key.pem`: `key.pem` must always match `cert.pem`, and a re-key in flight
has no certificate yet. `loadCreds` and `identity.Decide` never read it, so a pending key **cannot become an identity
by accident** — only `saveCreds` promotes it, and that promotion clears the pending file (all three success paths —
re-key, renewal, join-token enrolment — go through `saveCreds`).

**Two identities are tried per attempt, in order**, and only when a pending key SURVIVED an earlier attempt: the
fingerprint first (the only case where the control plane can already hold it), the serial second. On a first attempt
the fingerprint is skipped — the control plane cannot possibly know a key it has never been sent, so trying it would
spend a challenge to learn nothing. The agent cannot tell which case it is in, because refusals are uniform by
design; it does not need to, and each attempt is independently sound.

**Rate budget, recomputed honestly rather than inflated:** the binding case for `rekeyAttemptsPerMinute = 600` is a
whole fleet recovering after an outage, and in that case there is no pending key, so it is still 4 requests/min per
gateway. The two-identity path doubles a **single** node's rate, and only in the lost-response case. Left at 600,
with the tail stated: a fleet that ALL suffered lost responses would be throttled and converge more slowly — which
is a queueing delay, not a refusal, and the agent already distinguishes the two (review #10).

### What the reds cost to break

| red | mutation | result |
|---|---|---|
| `TestBothIdentifiersRefuseIndistinguishably` | ambiguity resolves to the first row | FAIL ✅ |
| `TestRekeyIssuesOverThePENDINGKeyNotAFreshOne` | `Rekey` mints its own CSR key | FAIL ✅ |
| `TestPendingKeyIsPersistedBeforeAnySubmit` | pending key minted fresh every call | FAIL ✅ |
| `TestLostResponseDoesNotBrickTheGateway` | *(the scenario itself — 4 steps against a real database)* | PASS |

The first mutation attempt at the pending-key red was a **build failure**, not a test failure — indistinguishable
from a pass under the harness rule this epic already learned. Redone so it compiled, and only then did it prove
anything.

### One defect the reds found in this work

An unrecognised `identifier_kind` reached the INSERT and returned a **CHECK constraint violation** — a 500,
distinguishable at a glance from the 403 every other refusal returns. Reachable only from a future caller, since
`ParseRekeyIdentifier` emits two kinds; validated in `IssueRekeyChallenge` as well, because the point of a second
layer is that the first one might change.

### A fixture hazard, found by tripping over it

The first version of the integration fixture COMMITTED, and `agentca.LoadOrCreate` **persists** a CA sealed under the
sealer it is given while correctly refusing to regenerate one it cannot decrypt. It therefore left a CA sealed under
a throwaway test key in the shared development database, and the next two tests failed with *"agent CA exists but is
unusable"* — the same message a real operator would get. Removed the row, and the fixture now runs inside ONE
transaction that rolls back (`Service.withTx` runs against `s.q` when `s.pool` is nil, which puts `Rekey`'s own
transaction inside the test's). **A test fixture that persists a sealed secret can brick the environment it runs in.**

### REGISTERED — the contract migration

`node_rekey_challenges.cert_serial` is written but never read by this version, and `identifier` is NULLABLE only
because `SET NOT NULL` would break a roll. Both resolve in ONE later migration, once no shipped version reads the
old column: drop `cert_serial`, set `identifier NOT NULL`, and collapse `coalesce(identifier, cert_serial)` back to
`identifier = $2`. **Trigger: the release after this one ships** — the expand/contract contract the guard exists to

## HALT-AND-SURFACE — is the cascade-restore path REACHABLE? (raised drafting the walk, 2026-07-30)

Desk-checking Leg 4 of `docs/S13-boxwalk.md` produced a question the build should have asked:

- `RestoreCascadeRevokedDevices` has exactly **one** caller — `nodes.Rekey`, after commit.
- Devices are cascade-revoked in exactly **one** place — `nodes.Revoke`.
- And **`Rekey` refuses a revoked node** (D3, amended precisely so a proof cannot overturn a human decision).

So the only trigger that produces `revoked_cause='cascade'` devices puts the node into the one state that can never
reach the code which restores them. On this reading **Wall 6's mechanism is unreachable in production** — correct
code wired to a trigger it cannot fire from, which is what the DORMANT-MACHINERY law names (S8.4, where a
dormant-until-next-story rider was ripped out rather than shipped).

**Not resolved here.** The faces, for disposition:

| face | what it means |
|---|---|
| (a) **Name a reachable trigger** | an operator action on a recovered gateway ("restore this gateway's devices"), which keeps the human in the loop that D3 insists on |
| (b) **Un-revoke** | rejected on sight, and stated so it is not re-proposed: it is exactly what D3 refuses |
| (c) **Remove the mechanism** | and re-open Wall 6 honestly — the gap goes back on the ledger rather than being covered by code that never runs |
| (d) **The analysis is wrong** | there is a path neither grep found; the walk's Leg 4 is written as a falsification attempt for precisely this |

Note the timing honestly: Slice 5 was built and reviewed *after* the D3 amendment, and neither the build, the reds,
nor the review asked whether the trigger could co-occur with the gate. The reds proved the restore does the right
thing **when called**; nothing proved it is ever called. **A unit test proves behaviour, never reachability** —
which is the same class as the who-reads-this probe (a producer without a consumer), one layer up: a consumer
without a reachable producer.
