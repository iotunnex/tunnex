## 2. Status Representation (`active` | `revoked` | `pending`), `health_blocked`, and `approved_by`

- **`status` Enum (`active`, `revoked`, `pending`):**
  - `active`: Normal functioning device. Renders `StatusDot` (on/off) and `lastSeen(...)`. Shows `Revoke` button.
  - `revoked`: Device revoked. Renders `<Badge tone="danger">revoked</Badge>`. Posture badges, `re-export needed`, and actions are **SUPPRESSED** via `d.status !== "revoked"`.
  - `pending`: Device awaiting admin approval under Enterprise device approval mode. Renders `<Badge tone="warn">pending</Badge>`. During issuance ceremony, `pendingExport` surfaces: *"This device is pending approval — the profile is valid but won't connect until an admin approves the device."*
- **Tone Vocabulary Alignment (One-Truth Across Screens):**
  - `Gateways.tsx` line 310 uses `<Badge tone="warn">` for degraded node warning states.
  - `Devices.tsx` uses `<Badge tone="warn">pending</Badge>` for pending approval state, ensuring consistent one-truth vocabulary across screens for non-active warning states.
  - **Tone Type Reconciliation:** `PostureBadge.tone` is `BadgeTone | "ok"` (`"warn" | "danger" | "unknown" | "ok"`). Posture cell renders via `<span className={postureBadgeClass(pb.tone)}>{pb.label}</span>` (mapping `"unknown"` to `"text-amber-300"`). It is NOT passed to `<Badge>`. `status === "pending"` badge IS rendered via `<Badge tone="warn">`, which accepts `"warn"` (`BadgeTone` in `ui.tsx` is `"ok" | "warn" | "danger" | "neutral"`). Both types align cleanly at compile time (`tsc -b`).
- **`health_blocked: true`:**
  - Enforcement fact: Device is excluded from every gateway while `true`. When `health_state === "noncompliant"` and `health_blocked === true`, renders `"posture blocked"`.
- **`approved_by: null` (Grandfathered):**
  - `approved_by: null` indicates a grandfathered / auto-approved device enrolled when device approval mode was off. Functions as active without requiring device approval queue action.

## 3. Posture States & Disk Encryption Tri-State

- **`health_state` (`compliant`, `noncompliant`, `unknown`, `undefined`):**
  - `undefined` (absent): Org has no posture checks configured. `postureBadge` returns `null` (no posture noise / no badge).
  - `health_blocked: true`: Returns `{ label: "posture blocked", tone: "danger" }`.
  - `noncompliant`: Returns `{ label: "posture warning", tone: "warn" }`.
  - `compliant`: Returns `{ label: "posture ok", tone: "ok" }`.
  - `unknown`: Returns `{ label: d.health_reported_at ? "posture stale" : "posture not reported", tone: "unknown" }`. **`unknown` MUST NEVER render as a pass** (absence is not compliance).
- **No-Posture-Checks Case (Seeded Payload Verification):**
  - OpenAPI Go struct `Device` (`apps/api/internal/api/api.gen.go:603`) defines `HealthState *DeviceHealthState json:"health_state,omitempty"`.
  - When an org has zero posture checks configured, the server sets `HealthState = nil`. JSON serialization omits the `health_state` key entirely (`omitempty`).
  - In TypeScript, omitted keys deserialize as `undefined`. `postureBadge(d)` evaluates `if (d.health_state === undefined) return null;` and returns `null`, omitting posture noise. `fixtures.sql` seeds open devices without health fields to mirror zero-checks orgs.
- **`health_disk_encrypted` Tri-State (`true`, `false`, `undefined`):**
  - `true` $\rightarrow$ `"encrypted"`
  - `false` $\rightarrow$ `"not encrypted"`
  - `undefined` $\rightarrow$ `"not reported"` (never an em-dash or guessed value).

## 4. Control Plane Status Header Pattern Audit

- `HealthStatus` (`control plane operational` / `control plane unreachable`) already exists in `AppShell.tsx` (line 322) and renders in the footer of EVERY page after querying `/healthz`.
- Hardcoding static text `control plane ● healthy` in individual page title headers (`Access.tsx`, `Devices.tsx`) is a **NEW, ad-hoc pattern** that multiplies the registered duplicate-render defect across screens and desyncs from live `/healthz` telemetry.
- **Rule:** Page headers MUST NOT hardcode static `control plane ● healthy`. Page titles render `<h1 ...>Devices</h1>` with org subtitle `{org.name}`. Shell-level footer owns control plane health.

## 6. Schema & Read-Path Verification

### Read-Path Verification for `Device.public_key`
- **Schema & Query Inspection:** Database column `devices.public_key` is `text NOT NULL DEFAULT ''` (`0010_devices.up.sql` / `0043_ovpn_keyless_device.up.sql`). `listDevices` query (`db/queries/devices.sql`) selects `public_key`.
- **Read-Path Serialization:** Server handler emits `public_key: ""` (empty string) for OpenVPN devices. TypeScript type `public_key: string` (required) matches read-path JSON payload 100%.
- **`fixtures.sql` Alignment:** Seeded OpenVPN device `ovpn-contractor` sets `public_key = ''` (empty string, not `NULL`).
