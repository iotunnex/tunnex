### HALF-FOLD INSTANCE 3 — #11, and it breaks my own heuristic

`decisions.md:1263` closes *"#11 promotion could leave a mixed pair"* with *"the promotion seam is injectable and
the save-failure path no longer terminates."* **Both exist** — `saveCredsFn` (`main.go:481-485`), the non-terminal
path (`:952-965`). **Neither prevents or detects a mixed pair.** The fix made the failure *testable* and
*survivable*; the named defect was never addressed. The boot-time pair check reported as folded **does not
exist**: `grep X509KeyPair apps/node/cmd/agent/main.go` returns nothing.

**I said single-claim rows were lower risk. #11 refutes that.** There are TWO half-fold mechanisms, and only one
is about claim counts:

1. **Majority-served** — a row closes N claims, the fix serves most of them; the outlier rides along on adjacency
   of subject (claims 2/4/13/20; claims 9/10/14).
2. **Adjacent-fixed** — a row closes ONE claim, and the fix addresses a *neighbouring* problem — the
   consequence, the testability, the survivability — rather than the defect named (#11).

**Mechanism 2 is the more dangerous**, because a single-claim row looks unambiguous and invites exactly the
generalisation I made. **The coverage question must be asked PER ROW regardless of claim count**, and the
question is *"does the cited fix make the named defect impossible?"* — not *"did an edit land here?"*, which is
what the 41-marker sweep asked and what #11 passed.

## E. saveCreds ORDERING — RULED REAL. The comment is wrong AND the order is wrong.

**Second instance of a comment on this function vouching for a property the code lacks** (pass 1 #11 was the
first). There is **no boot-time pair check** — `grep X509KeyPair apps/node/cmd/agent/main.go` returns nothing.
The only pair validation is inside `control.NewClient` (`client.go:90`), whose failure path is `os.Exit(1)`.

**The comment** (`main.go:441-442`): *"the KEY is renamed LAST … if the sequence is interrupted, the old key
still matches the old certificate and the agent remains recoverable."*

**Both halves fail.** Order is `ca.pem`, `cert.pem`, `key.pem`. An interruption between the second and third
rename leaves **NEW cert + OLD key** — the old certificate is already gone, so "the old key still matches the old
certificate" is false on its face. And the resulting state is the **unrecoverable** one:

| interrupted state | what `Decide` does | outcome |
|---|---|---|
| **NEW cert + OLD key** (today's order) | the new cert is **valid**, so `UseStored` | `NewClient` → `X509KeyPair` fails → `os.Exit(1)` → restart → **identical state** → CrashLoopBackOff. `Decide` never reaches `Recover`, because nothing about the certificate is expired |
| **OLD (expired) cert + NEW key** (key first) | expired → **`Recover`** | `attemptRekey` runs, the pending key file still exists (`saveCreds` removes it only at the end), the fingerprint identity is available → recoverable |

**Ordering alone is not the whole fix.** In the RENEW path the old certificate is still valid, so cert-last gives
old-valid-cert + new-key — a mismatch that also lands in `UseStored` and crash-loops. **The robust fix is a
pair check at load that routes a mismatch into `Recover` instead of `os.Exit`**, since a mismatched pair is
precisely a case proof-of-possession can repair.

**Ruled: REAL. Owed a red.** The comment must be corrected in the same change, not left describing an intent.
