# 2. ⛔ THE JOIN TRAP — TESTED, NOT REASONED

**The concern:** `RoutedRanges.ranges` is *"canonical masked form, sorted"*; `SiteSubnet.cidr` is documented
only as *"IPv4 CIDR of the routed LAN"*. A subnet stored as `10.20.0.1/24` would never string-match a range
emitted as `10.20.0.0/24`, **and the row would render unattributed — reassuring-empty at row level.**

**MEASURED. THE TRAP CANNOT FIRE, AND THERE ARE TWO INDEPENDENT REASONS:**

```
$ … pg_attribute → site_subnets.cidr type = cidr        ← the POSTGRES cidr type
$ SELECT '10.20.0.1/24'::cidr;
  ERROR:  invalid cidr value: "10.20.0.1/24"
  DETAIL: Value has bits set to right of mask.
```

**1 · THE COLUMN TYPE REJECTS HOST BITS.** A non-canonical subnet cannot be stored *at all* — not by the API,
not by a migration, not by a hand-written `INSERT`. **This is the strong guarantee: it holds against write
paths that do not exist yet.**

**2 · AND THE WRITE PATH MASKS ANYWAY** — `service.go:96`: `AddSiteSubnet(… Cidr: cidr.Masked())`. Belt and
braces, and the belt is the database.

**SO A STRING JOIN IS SAFE — but the code will still normalise both sides**, because the *reason* it is safe
lives in a column type two layers away, and a future migration to `text` would break the join silently.
`routedranges.go:211` already sets the precedent: `ss.Cidr.Masked() == cidr.Masked()`.

**⚠ THE OWED RED IS STILL OWED, IN A DIFFERENT FORM.** The founder asked for a test proving a non-canonical
stored subnet still attributes. **That test cannot be written — the insert is rejected.** So the guard becomes
the honest one: **a test asserting the DB refuses a non-canonical CIDR**, which is what actually protects the
join. *A test that cannot be written because the state is unreachable is a stronger result than a test that
passes.*

# 3. RENDER-FLOOR ITEMS

**`forwards` IS GATED.** A forward appears only when its `resolver_ip` falls inside a routed range. **Empty
means "none reachable", NEVER "none configured."** Copy must not say *"no DNS forwards configured"* — the
honest empty state is *"No forwarded zones are currently reachable from a routed range."* The handoff already
carries the rule verbatim: *"A forward is handed to devices only when its resolver falls inside a routed
range — never a SERVFAIL generator."*

**`dial_endpoint` / `dial_pubkey` ARE NULL IN TWO DIFFERENT CASES**: no `device_id` was passed, **and** the
device's node is not a hub-set member. **Null must not render as "no hub."** This screen passes no
`device_id`, so they are *always* null here — **the fields are therefore not rendered at all**, rather than
rendered as an absence that means something.
